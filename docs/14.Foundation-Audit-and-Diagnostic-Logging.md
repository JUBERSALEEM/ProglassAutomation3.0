### Where it lives

`%APPDATA%\ProGlassAutomation\Logs\proglass-errors.log` — the product's one
app-data root (`AppDataRoot`), the same folder the databases already live in, so
a backup carries the diagnostics with it. Never the repository, the working
directory, the executable folder or a temp folder. **The folder and the file are
created by the first failure**, not at startup: a clean run leaves nothing.

### Bounded

1 MB per file, 5 files, oldest deleted first — at most 5 MB of disk in total. One
record per failure; an identical failure repeating inside a 10-second window is
counted, not re-written, and the count is emitted with the next distinct record.
A single record is itself clamped at 64 KB, with the character budget set to a
quarter of the byte budget so a four-byte character cannot overflow it; a clamped
record ends with `[record truncated: N bytes, limit 65536]` instead of looking
complete. Without that clamp one pathological stack trace could have exceeded the
whole file budget in a single entry and made "bounded" untrue.

### Failure-only — what is deliberately *not* written

Startup, navigation, successful sign-in, session resumed, successful save,
successful theme change, heartbeats, polls, ordinary validation feedback (a
missing company name, a duplicate username, "no client matches that search").
The gate caps the number of call sites (25; there are 18) and refuses an
operation id that names a routine event.

### Redaction

Passwords, hashes, salts, tokens, secrets, API keys and connection strings are
masked by name; runs of 12+ digits, groups of three or more 4-digit blocks (IBAN
shape) and e-mail addresses are masked by shape. If the redaction step itself
fails the entry is replaced with `[entry withheld: the redaction step failed]` —
never written unscrubbed. User names, client names and inquiry text are not
written *at all* by this round's call sites; the operation id is the identifier.

### Process traps

| Trap | Behaviour | Honest limit |
|---|---|---|
| `DispatcherUnhandledException` | Recorded as FATAL, the operator is told in a message box (including where the record is), then the application closes through `Shutdown(1)`. `Handled = true` exists only so the runtime does not abort mid-unwind before that shutdown. | Nothing here knows which screen state survived, so continuing would be a guess, not a recovery. Unsaved work in the failing operation can be lost — that is the price of not writing onto a half-updated form. |
| `AppDomain.CurrentDomain.UnhandledException` | Recorded as FATAL with `IsTerminating`. | The runtime is already terminating. There is no `Handled` here; the message box and any unsaved work are lost. |
| `TaskScheduler.UnobservedTaskException` | Recorded as ERROR. | Fires only when the faulted task is finalised and nothing observed it — possibly minutes later, and not at all if the process exits first. |

Attachment is two-phase on purpose: the `App` type's static constructor runs
*before* `OnStartup`, so it takes the AppDomain and task traps and — when there is
no `Application` object yet — leaves the dispatcher trap for the second call in
`OnStartup`. The dispatcher flag is tracked separately, because an "already
attached" early return would have silently lost that trap for the life of the
process. That ordering is what makes a fault in `App`'s own construction
(`ThemeService`, XAML load) recordable at all.

Best effort on the fatal path: the record is flushed to disk (`Flush(true)`)
before the handler returns, because a terminating process has no guarantee of a
later flush. A logging failure can never mask the original exception: every
write path returns `bool`, holds the fault in `LastFailure`, and carries a
thread-static recursion guard.

## 8. Known gaps and risks

1. **Placement — decided 2026-10-28 (round 34).** `Diagnostics/` stays at the
   repository root as unnumbered shared application infrastructure: not moved
   into Inquiry, no business-module number assigned, registry entry in `docs/06`
   kept, failure-only policy preserved. `docs/00` forbids inventing a feature
   number, and this is how the folder satisfies that rule without pretending to
   be a module.
2. **46 silent `catch` blocks remain**, and two register-load failures
   (`step2.c.2`, `step3.c.2`) are shown on screen but not recorded — both files are
   frozen by rule K and were left alone rather than split for one line. Each was read and classified; 4 are gaps
   (§I6–I8 and T5) and all four sit in the frozen Inquiry module or in a path
   whose failure the next save retries. They are not defects this round was
   authorised to change.
3. **A dispatcher fault closes the application.** Round 33 kept the shell up after
   an unhandled UI fault; round 34 replaced that with record → tell the operator →
   `Shutdown(1)`, because nothing in the process knows which screen state survived
   and a half-updated form is worse than a closed application. The cost is real:
   work in the failing operation is lost. `Handled = true` is set only so the
   runtime unwinds into that shutdown instead of aborting mid-frame.
4. **`AppDomain` faults can lose the record** if the process dies before the
   flush; the flush is best-effort and is documented as such, not promised.
5. **Unobserved task faults are late by nature** — they show up when the task is
   finalised, which may be after the user has moved on, or never.
6. **No log viewer in the UI.** The path is printed nowhere; the owner has to
   know `%APPDATA%\ProGlassAutomation\Logs`. Deliberate: a viewer is a module of
   its own, and this round was authorisation for logging only.
7. **Build/run unverified** (see §6.2) — the first thing the owner should do is
   compile, launch, break something on purpose and confirm one record appears.
8. **Residual personal data in exception text.** Redaction masks credentials by
   name and long numbers / e-mail addresses by shape, but a database or filesystem
   error message can still quote a customer name or a path containing the Windows
   account (for example `C:\Users\<name>\…`). Builds and support conversations
   need the path to act on it; the trade is recorded here rather than hidden.
9. **The Client attribution gap is unchanged** (§7): the client table carries
   timestamps but no operator, so the log is currently the only place a client
   write failure can be attributed, and only to "a failure happened".
10. **A stored logo whose file has gone was silently ignored** — found by the
    first-ever run of `step4.f.1` (round 34.3), not by any source check. The
    editor resolved the stored name through `CompanyLogoStore.ResolvePath`, which
    returns `null` when the file is missing, so the preview concluded "no logo":
    nothing on the page, no explanation, while the database still named a logo
    that would not print. The loader's own message for this case ("The image file
    is not on disk. Choose the logo again.") was unreachable. Fixed by resolving
    the stored *pointer* (`PathForStoredName`) for the preview and keeping the
    existence-checked path for printing and deletion; `step4.f.2` now fails if the
    preview goes back to the existence check.
11. **A saved address disagreed with the address it prints** — found by the
    second executed run of `step4.f.1` (round 34.5), after the newline mask was
    removed. `NormalizeAddress` trimmed each line and then *collapsed* runs of
    blank lines to a single empty one, keeping a paragraph break; docs/12 says
    "blank lines dropped". The letterhead renderer
    (`CompanyProfileLogoViewModel.AddressLines`) skips every blank, so an
    operator who pasted `Shop 4`, a gap, `Main Road`, `Ajman` saved four lines
    and saw three — the stored value and the document it feeds could never agree,
    and nothing told them. Fixed by dropping blanks outright, which is what both
    the rule and the renderer already meant; `step4.f.2` now fails if either side
    keeps a blank, and the compiled check covers a single gap, a run of gaps and
    an address of nothing but gaps.

12. **The owner's full build reports these five code warnings** (2026-10-28, none
    introduced by the logging work; recorded, deliberately not cleaned up, because
    warning cleanup was out of scope and each is its own small decision):
    `CS4014` `InquirySupport.cs(89,25)` fire-and-forget `BeginInvoke`;
    `CS8600` `SchemaMigrationRunner.cs(90,37)` null-literal conversion;
    `CS0168` `step3.c.3.FirstRunViewModel.cs(273,30)` unused `ex` in a catch — the
    only one of the five that touches the failure-only rule and would be fixed by
    recording that exception rather than renaming the variable;
    `CS0414` `step4.c.1.CompanyProfileViewModel.cs(75,24)` `_savedSummary` assigned
    and never read; `WFAC010` `app.manifest` still carries high-DPI settings.
