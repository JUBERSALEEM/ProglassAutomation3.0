# 10 — The list-page pattern (standing contract)

Status: **binding on every list page.** Two pages implement it today — Clients
(`step2.ClientManagement/step2.d.1.ClientWorkspaceView.xaml`) and Inquiries
(`Inquiry/Views/InquiryListView.xaml`). Proforma Invoices, Job Orders, Delivery
Notes, Tax Invoices and Statements will be built this way; they do not get to
invent a different one.

Owner direction that produced this document:

> "apply same in inquiry page … then all upcoming list pages will follow same
> pattern. all received prepared sent confirmed etc move to dropdown single
> section. same for proforma invoice job order etc"

## 1. The shape

A list page is four rows and nothing else:

```
Row 0  Plate      one command bar
Row 1  Plate      advanced filters, Collapsed unless asked for
Row 2  Card       the register, spanning all remaining height
Row 3  DockPanel  page status + pager
```

`RowDefinitions = Auto / Auto / * / Auto`. The register owns the `*`, so it
reaches the bottom of the page. There is no fifth row, no strip under the
register, and no card wall above it.

### Row 0 — the command bar

One `Plate`, one row of controls, everything vertically centred:

| Slot | Content |
| --- | --- |
| left | **Status** dropdown → `StatusTabs`, `DisplayMemberPath="LabelWithCount"` |
| left | **Module** dropdown → `ModuleTabs`, per-item template (planned items muted + " (soon)") |
| middle | one caption line: the page's headline numbers (pipeline, counts) |
| right | search field + watermark · **Filters** toggle · one primary action · **⋯** overflow |

Rules:

- **State lives in dropdowns, never in strips.** Seven buttons across the page
  for All/Received/Prepared/Sent/Confirmed/Hold/Cancelled is a full-width strip
  of chrome that pushes the register down. One `ComboBox` says the same thing and
  carries each state's live count in its label.
- **Module switching is a dropdown too**, and a module that is not routed yet is
  listed with `IsEnabled => !IsPlanned` so the user can see the roadmap without
  being able to walk into an unbuilt page. The view model re-notifies the
  selection on the dispatcher, or the control keeps showing the refused item.
- **Exactly one primary action** in the bar (`PrimaryButton`), always visible. A
  secondary action that is not frequent enough to own a slot goes in the `⋯`
  overflow, which is a `Button` + `ContextMenu` pair. `Button.ContextMenu` only
  opens on right-click, so the view needs one `Click` handler that sets
  `PlacementTarget` and `IsOpen`.
- **The search box is visible, always.** It is the one filter that must never be
  hidden behind a toggle.
- **The bar carries no page title.** The shell banner already shows where the
  user is; a second title spends a row on nothing.

### Row 1 — advanced filters

Same `Plate` idiom, one `UniformGrid Rows="1"`, collapsed by default:

- `Visibility` is driven by `AreFiltersExpanded` through a `DataTrigger` on a
  wrapper element — never by setting `Style` twice on one element (an attribute
  and a `<X.Style>` element is the error "Style set twice").
- The **Reset** button lives here, with the controls it resets.
- The toggle's label names the state and the count: `Filters`,
  `Filters (3)` when a hidden filter is narrowing the register, `Hide filters`
  when open. A collapsed row must never hide a filter silently.

### Row 2 — the register

A `Card` holding an error surface, the `DataGrid`, and an empty state that keeps
its own call to action.

**The register itself is the shared style. Write three attribute values and you
have the whole pattern** — do not author a header template, a cell template, a
text style or a column width. They exist once, in every theme package.

```xml
<DataGrid Style="{StaticResource ListGrid}"
          ItemsSource="{Binding Rows}"
          SelectedItem="{Binding SelectedRow, Mode=TwoWay}">
    <DataGrid.Columns>
        <DataGridTextColumn Header="Number"  Binding="{Binding NumberText}"
                            ElementStyle="{StaticResource ListMonoText}" />
        <DataGridTextColumn Header="Client"  Binding="{Binding ClientName}"
                            ElementStyle="{StaticResource ListStrongText}" />
        <DataGridTextColumn Header="Updated" Binding="{Binding UpdatedText}"
                            ElementStyle="{StaticResource ListText}" />
    </DataGrid.Columns>
</DataGrid>
```

**Every one of those four references is a `StaticResource`.** Three of them are
load-bearing in a way that is invisible in review: `Style` resolves when the page
is parsed, and `ElementStyle` is a plain CLR property that ignores a
`DynamicResource` outright. A `DynamicResource` that has not yet found its key
does not fail — it renders the default, which is left-aligned, unbolded and
untrimmed. That is how the register shipped twice with the band in place and the
text wrong. The parse-time form fails loudly at parse time instead.

| Key | What it gives you |
| --- | --- |
| `ListGrid` | read-only single-row selection, one header band, **no body grid lines**, **`ColumnWidth="*"` so every column takes an equal share**, `ControlMinWidth` floor, the theme's outside margin |
| `ListColumnHeader` | the heading is **bold (`FontWeight="Bold"`)**, **centred (`HorizontalContentAlignment=Center`)**, and sits in a **ruled band** — the header's own `BorderBrush=BorderStrong`, `BorderThickness=0,0,1,1`. **No `Template`:** the framework's header template lays the label out with the header's `HorizontalContentAlignment`, which is how the master app's `ErpDataGridColumnHeaderStyle` works and is the only arrangement that has ever rendered centred here |
| `ListCell` | the value is **centred**, the cell draws **no border**, and the theme keeps selection, hover and focus |
| `ListText` | the value trims with an ellipsis, **and a hover opens the product's tooltip with the full text** — `ToolTip="{Binding Text, RelativeSource={RelativeSource Self}}"`, no code |
| `ListMonoText` / `ListStrongText` | the same, for codes/dates and for the identifying column |

Rules that follow from it:

* **A column never sets `Width`.** An equal share is what makes every column fit;
  a pixel count is a guess that clips the moment the font or the window changes
  (it clipped the project timestamps and the inquiry numbers for two rounds).
  If a value is too long for its share it trims, and the tooltip reveals it.
* **A column never carries a header template.** `Header="…"` is centred, ruled
  and bolded by the header style. Two traps, both shipped:
  - a nested `<DataGridTemplateColumn.Header>` element is printed as its type
    name by a string header, and a `TextBlock` there is a *local* value, so no
    style can weigh or centre it;
  - a hand-written `ControlTemplate`, on the register's header style **or on the
    package's implicit `DataGridColumnHeader` style it derives from**. Both
    existed. The implicit one's presenter had no horizontal alignment at all, so
    it won over everything the register asked for and every label rendered flush
    left; and no style can weigh text the template never binds. The rule is now:
    **no `ControlTemplate TargetType="DataGridColumnHeader"` anywhere in a
    package.**
* **`FontWeightHeading` is not bold.** The token resolves to **SemiBold** in
  every package. A heading that must read as bold says `FontWeight="Bold"`; the
  token is for the app's heading *scale*, not for a column heading the owner has
  to squint at.
* **A cell's `ContentPresenter` is `HorizontalAlignment="Stretch"`.** Bound to
  `HorizontalContentAlignment` (a centred value) it shrinks to the text, so the
  `TextBlock` inside it can never be wider than its own glyphs and
  `TextAlignment=Center` centres nothing — the value renders at the left edge
  with no error and no log line. Full-width presenter, centred text; a chip or a
  button in a template column centres **itself** with
  `HorizontalAlignment="Center"` on its root.
* **The hover bubble is a binding, not a behaviour.** The value style carries
  `ToolTip="{Binding Text, RelativeSource={RelativeSource Self}}"`, and the
  product has **one** implicit `ToolTip` style (`step1.e.6.PopupsAndScroll.xaml`)
  — wrapped, `MaxWidth=PopupMaxWidth`, theme surface, never trimmed — which is
  how the master app does it (`TextTrimming="CharacterEllipsis"
  ToolTip="{Binding …}"` + one `AppToolTipStyle`). Nothing measures a cell,
  nothing intercepts the mouse, nothing is allocated on hover, and the bubble is
  open before the pointer settles. The round-52/53 behaviour measured every cell
  on layout *and* on enter, built a `ToolTip` object per hover, and could throw
  from WPF's tooltip service; the owner's words for it were "slow and ugly".
* **No `ToolTip` element claims `StaysOpen`.** The tooltip assigned to the
  `ToolTip` property is opened and closed by WPF's `PopupControlService`, which
  throws `NotSupportedException` on the dispatcher when the element says
  `StaysOpen="False"` — a FATAL for a cosmetic feature, raised the moment the
  pointer rests on a clipped cell.
* **An editable entry grid is not a register.** The inquiry editor's BOQ lines
  keep their own widths and say `IsReadOnly="False"`; the register style is
  read-only and must not be put on one.
* File actions keep their own `Actions` column **with a real header**.
* **`ElementStyle` takes a `StaticResource`, never a `DynamicResource`.** It is a
  plain CLR property on `DataGridColumn`, and `DynamicResource` can only drive a
  DependencyProperty — so the markup is accepted, ignored, and the column keeps
  the default left-aligned untrimmed `TextBlock`. This is exactly what shipped in
  round 51 and what the owner saw on screen: the header band and the equal widths
  (a real `Style` on the `DataGrid`) worked, every value stayed left-aligned. A theme switch still repaints, because the style's own setters are
  `DynamicResource` tokens.

`step1.d.20.ListPatternChecks.py` enforces all of the above and **discovers the
pages**, so the next module is covered the day it is added rather than the day
somebody remembers to add it to a list.

### Row 3 — the footer

`DockPanel`: pager buttons docked right, page indicator, loading text, and
`PageStatus` — printed **once**, here, next to the pager.

## 2. The view-model contract

A page's list view model exposes these names. The view binds them by name, so
deviating means editing the view, which means the pattern has stopped being one.

| Member | Kind | Purpose |
| --- | --- | --- |
| `StatusTabs` | `ObservableCollection<T>` | one item per state, in workflow order |
| `SelectedStatusTab` | two-way item property | delegates to the page's existing status key and reloads |
| `ModuleTabs` | `ObservableCollection<T>` | live module first, then planned modules |
| `SelectedModuleTab` | two-way item property | refuses planned items and snaps back |
| `AreFiltersExpanded` | `bool` | collapsed by default |
| `ToggleFiltersCommand` | `ICommand` | flips it |
| `FiltersToggleLabel` | `string` | `Filters` / `Filters (n)` / `Hide filters` |
| `ActiveFilterCount` | `int` | advanced filters currently applied, search excluded |
| `PageStatus` | `string` | one line, footer only |
| `HasActiveFilters`, `ResetFiltersCommand`, paging commands | — | unchanged from the existing page |

Status items expose `Key`, `Label`, `Count`, `LabelWithCount`; **a count change
must re-notify `LabelWithCount`**, because that is the property the dropdown
binds — notifying `CountText` alone leaves a stale number on screen.

## 3. Checklist for a new page (PI, JO, DN, TI, Statements)

1. Copy the four-row skeleton; do not copy the old three-card layout.
1a. Name the three pattern keys (`ListGrid`, `ListText`/`ListMonoText`/
   `ListStrongText`) and nothing else for the grid. No widths, no header
   templates, no local cell styles (see Row 2).
2. Reuse the page's existing filter properties. The dropdown and the collapsible
   row are chrome changes, not query changes.
3. Keep every existing entry point reachable: import, export, inbox, refresh,
   reset, new record, row actions. If one moves into the overflow, the guard for
   that page must still find it.
4. Planned sibling modules are listed, disabled, and labelled `(soon)`.
5. Delete what the bar replaced: chip `Style`s, chip strips, hero/KPI cards,
   the filter card, the footer strip. Dead styles are dead code.
6. Add or extend that page's guard test: assert the dropdown bindings are
   two-way, the primary action is in the bar, the filter row is bound to
   `AreFiltersExpanded`, `PageStatus` appears once, and no `UniformGrid Columns="7"`
   strip has returned. Verify the guard fails when mutated — a guard that cannot
   fail is decoration.

## 4. Anti-patterns (all removed at least once)

- a chip strip per dimension, however tidy it looks;
- three KPI cards repeating numbers a caption can say in one line;
- a separate card for "Actions" that owns Import/Export and costs a row;
- a strip under the register repeating the selected row;
- `Style="…"` plus `<X.Style>` on the same element;
- **`DisplayMemberPath` on a `ComboBox`.** The closed control renders
  `SelectionBoxItem` through `SelectionBoxItemTemplate`, and `DisplayMemberPath`
  never fills that template — the box prints the item's type name. Use an
  `ItemTemplate`. (`ListBox` is unaffected: it has no selection box.)
- text that is printed twice because nothing was deleted when it moved.
