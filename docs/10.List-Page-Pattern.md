# 10 — The list-page pattern (standing contract)

Status: **binding on every list page.** Two pages implement it today — Clients
(`step2.ClientManagement/step2.d.1.ClientWorkspaceView.xaml`) and Inquiries
(`Inquiry/Views/InquiryListView.xaml`). Proforma Invoices, Job Orders, Delivery
Notes, Tax Invoices and Statements will be built this way; they do not get to
invent a different one.

Owner direction that produced this document:

> "apply same in inquiry page … then all upcoming list pages will follow same
> pattern. all received prepared sent confirmed etc move to dropdown single
> section. same for proforma invoice job order etc"

## 1. The shape

A list page is four rows and nothing else:

```
Row 0  Plate      one command bar
Row 1  Plate      advanced filters, Collapsed unless asked for
Row 2  Card       the register, spanning all remaining height
Row 3  DockPanel  page status + pager
```

`RowDefinitions = Auto / Auto / * / Auto`. The register owns the `*`, so it
reaches the bottom of the page. There is no fifth row, no strip under the
register, and no card wall above it.

### Row 0 — the command bar

One `Plate`, one row of controls, everything vertically centred:

| Slot | Content |
| --- | --- |
| left | **Status** dropdown → `StatusTabs`, `DisplayMemberPath="LabelWithCount"` |
| left | **Module** dropdown → `ModuleTabs`, per-item template (planned items muted + " (soon)") |
| middle | one caption line: the page's headline numbers (pipeline, counts) |
| right | search field + watermark · **Filters** toggle · one primary action · **⋯** overflow |

Rules:

- **State lives in dropdowns, never in strips.** Seven buttons across the page
  for All/Received/Prepared/Sent/Confirmed/Hold/Cancelled is a full-width strip
  of chrome that pushes the register down. One `ComboBox` says the same thing and
  carries each state's live count in its label.
- **Module switching is a dropdown too**, and a module that is not routed yet is
  listed with `IsEnabled => !IsPlanned` so the user can see the roadmap without
  being able to walk into an unbuilt page. The view model re-notifies the
  selection on the dispatcher, or the control keeps showing the refused item.
- **Exactly one primary action** in the bar (`PrimaryButton`), always visible. A
  secondary action that is not frequent enough to own a slot goes in the `⋯`
  overflow, which is a `Button` + `ContextMenu` pair. `Button.ContextMenu` only
  opens on right-click, so the view needs one `Click` handler that sets
  `PlacementTarget` and `IsOpen`.
- **The search box is visible, always.** It is the one filter that must never be
  hidden behind a toggle.
- **The bar carries no page title.** The shell banner already shows where the
  user is; a second title spends a row on nothing.

### Row 1 — advanced filters

Same `Plate` idiom, one `UniformGrid Rows="1"`, collapsed by default:

- `Visibility` is driven by `AreFiltersExpanded` through a `DataTrigger` on a
  wrapper element — never by setting `Style` twice on one element (an attribute
  and a `<X.Style>` element is the error "Style set twice").
- The **Reset** button lives here, with the controls it resets.
- The toggle's label names the state and the count: `Filters`,
  `Filters (3)` when a hidden filter is narrowing the register, `Hide filters`
  when open. A collapsed row must never hide a filter silently.

### Row 2 — the register

A `Card` holding an error surface, the `DataGrid`, and an empty state that keeps
its own call to action. One header band, rules in the header band only, no rule
per body cell, numbers and statuses centred, file actions in an `Actions` column
with a real header.

### Row 3 — the footer

`DockPanel`: pager buttons docked right, page indicator, loading text, and
`PageStatus` — printed **once**, here, next to the pager.

## 2. The view-model contract

A page's list view model exposes these names. The view binds them by name, so
deviating means editing the view, which means the pattern has stopped being one.

| Member | Kind | Purpose |
| --- | --- | --- |
| `StatusTabs` | `ObservableCollection<T>` | one item per state, in workflow order |
| `SelectedStatusTab` | two-way item property | delegates to the page's existing status key and reloads |
| `ModuleTabs` | `ObservableCollection<T>` | live module first, then planned modules |
| `SelectedModuleTab` | two-way item property | refuses planned items and snaps back |
| `AreFiltersExpanded` | `bool` | collapsed by default |
| `ToggleFiltersCommand` | `ICommand` | flips it |
| `FiltersToggleLabel` | `string` | `Filters` / `Filters (n)` / `Hide filters` |
| `ActiveFilterCount` | `int` | advanced filters currently applied, search excluded |
| `PageStatus` | `string` | one line, footer only |
| `HasActiveFilters`, `ResetFiltersCommand`, paging commands | — | unchanged from the existing page |

Status items expose `Key`, `Label`, `Count`, `LabelWithCount`; **a count change
must re-notify `LabelWithCount`**, because that is the property the dropdown
binds — notifying `CountText` alone leaves a stale number on screen.

## 3. Checklist for a new page (PI, JO, DN, TI, Statements)

1. Copy the four-row skeleton; do not copy the old three-card layout.
2. Reuse the page's existing filter properties. The dropdown and the collapsible
   row are chrome changes, not query changes.
3. Keep every existing entry point reachable: import, export, inbox, refresh,
   reset, new record, row actions. If one moves into the overflow, the guard for
   that page must still find it.
4. Planned sibling modules are listed, disabled, and labelled `(soon)`.
5. Delete what the bar replaced: chip `Style`s, chip strips, hero/KPI cards,
   the filter card, the footer strip. Dead styles are dead code.
6. Add or extend that page's guard test: assert the dropdown bindings are
   two-way, the primary action is in the bar, the filter row is bound to
   `AreFiltersExpanded`, `PageStatus` appears once, and no `UniformGrid Columns="7"`
   strip has returned. Verify the guard fails when mutated — a guard that cannot
   fail is decoration.

## 4. Anti-patterns (all removed at least once)

- a chip strip per dimension, however tidy it looks;
- three KPI cards repeating numbers a caption can say in one line;
- a separate card for "Actions" that owns Import/Export and costs a row;
- a strip under the register repeating the selected row;
- `Style="…"` plus `<X.Style>` on the same element;
- **`DisplayMemberPath` on a `ComboBox`.** The closed control renders
  `SelectionBoxItem` through `SelectionBoxItemTemplate`, and `DisplayMemberPath`
  never fills that template — the box prints the item's type name. Use an
  `ItemTemplate`. (`ListBox` is unaffected: it has no selection box.)
- text that is printed twice because nothing was deleted when it moved.
