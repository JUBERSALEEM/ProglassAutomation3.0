# 00 — Project rules: authoritative naming specification

Read [AGENTS.md](../AGENTS.md) first. This document owns naming; the [registry](06.Feature-Registry.md) owns allocation and the [roadmap](04.Project-Roadmap.md) owns phase gates.

## Allocation and scope

- Every application-owned feature root begins with its unique sequential `stepN` identifier and an approved descriptive name.
- `step1` is Theme Studio. `step2` is Client Management (owner approval 2026-10-27, `inquiries.db` migration 1011). On **2026-10-27** the owner established the remaining implementation order and allocated `step3`–`step11` in it: User Management, Company Profile, Project Records & Inquiry Integration (foundation; `step3` was authorized and implemented on 2026-10-27, `step4`–`step5` still need their own approval), then Proforma Invoice, Job Order, Delivery Note, Tax Invoice, Statement and Reports (blocked by gate `G1`). The order, the gate and the boundaries live in [the business-module roadmap](11.Business-Module-Roadmap.md); allocation is not authorization. Never reuse a number, including after retirement; retain retired entries in the registry.
- Allocate the next unused feature number only after explicit owner approval of its name and scope; record approval evidence and update the registry, roadmap, and feature README together. Never invent future features.
- Unexpected unnumbered application files must be reported by exact path and require clarification before modification/deletion; their origin must not be assumed, and they are not a precedent for new V3.0 features. Shared application-owned concerns need an approved allocation/placement decision, not an invented unnumbered feature.

## Hierarchy

A child inherits its complete parent's identifier and adds one segment. At the feature root, use alphabetic siblings (`a`, `b`, `c`); within such a branch use numeric siblings (`1`, `2`, `3`), and continue with numeric segments only if necessary. Allocate sibling identifiers distinctly within the parent. The same prefix may identify a folder and its descendants, but do not assign the same sibling identifier to unrelated files/folders. Keep structures shallow and purposeful; do not build an empty tree.

## Theme architecture and stable-name exceptions

All theme-related implementation and concrete theme design specifications live under `Theme/` in the designated project root. Shared code still belongs to the existing **step1** allocation; this is not a new feature number. Root governance and feature workflow docs remain in their documented locations and link here.

### Source location and numbering

This tree supersedes earlier engine-inside-Studio examples. `step1.a` has one shared-engine branch under Theme; do not also create it under step1.ThemeStudio. Inside numbered branches, inherit the actual parent prefix. Within stable named theme directories, number additional app-owned implementation files where compatible using the existing step1 hierarchy; assign any needed branch identifier once in the feature documentation, distinct from a/b/c, not a second theme-specific scheme or an automatic feature number from theme order. No additional identifiers/files are allocated merely to complete a diagram.

Bento validation expectations and compiled package tests now use `Theme/step1.d.tests/` (`step1.d.ThemeTests.csproj`, Windows checks and Python source/regression checks); Studio behavior tests belong with Studio. Allocate each branch distinctly and document responsibility without creating empty test trees. The framework test project may retain a tool-compatible filename. Avoid embedding palettes or duplicate contract definitions in tests.

If actual technical constraints require another theme implementation location, document the reason and obtain approval before deviating. Views and conventional application bootstrap files may reference the shared engine/dictionaries; they must not own theme definitions or switching implementations.

### XAML/code-behind pairing compatibility

The master illustrates `step1.b.1.ThemeStudioView.xaml` with `step1.b.2.ThemeStudioView.xaml.cs`. WPF tooling commonly pairs by the identical XAML basename plus `.cs`. Prefer the matching pair shown in the tree: both use `step1.b.1`, representing **one paired view**, not accidental identifier reuse. This is an explicit tooling-compatibility exception to separate file numbering; leave `step1.b.2` unused rather than adding a filler file. A split `b.1`/`b.2` pair is permissible only after verifying explicit project/tool association and documenting it. Do not sacrifice build/designer compatibility to match illustrative filenames.

Dotted/hyphenated filenames do not become C# identifiers. Use legal descriptive class names/namespaces and keep `x:Class`, code-behind, generated items, resource URIs, build actions, and project references consistent. Verify the actual build before claiming compatibility.

### Feature-identifier convention (decided 2026-10-27)

One sequential number per approved feature — `step1`, `step2`, `step3`, … — allocated in the approved order and never reused. **Dotted sub-identifiers are not feature identifiers:** `step2.1`, `step2.2`, `step2.3`, `step2.4` (and `step3.1` onward) do not exist here and must not be created; order is expressed by the allocated number, never by a dotted variant of another feature's number. This generalises the 2026-10-27 decision-log rule that `STEP 2.1` is not a repository identifier.

Child identifiers inside a feature follow the hierarchy above: `stepN.a.FeatureView.xaml` and `stepN.b.FeatureViewModel.cs` at the feature root, with `stepN.c.tests/stepN.c.1.FeatureViewModelTests.cs`; in a nested `stepN.a/` branch use `stepN.a.1.FeatureView.xaml`. Child identifiers for `step4` onward are recorded when that module's plan is approved, not in advance; `step3`'s are recorded in the registry because it was authorized. `step2.NextFeature/` and `stepN.FeatureName/` remain illustrations, never names. Theme order numbers are not feature numbers: the second theme did **not** allocate step2.

## Framework/tool compatibility exceptions

Keep required conventional names when tools require or depend on them: `AGENTS.md`, root `README.md`, `.gitignore`, `.gitattributes`, solution/project names ending `.sln`, `.slnx`, `.csproj`, and workflow/configuration filenames. Framework entry points such as `App.xaml` may retain conventional names where verified tool behavior requires them. Record each new exception and reason in the owning README or decision log; do not create these files merely because an exception exists.

Root governance and the `docs/00`–`docs/06` documents are deliberate project-wide documentation exceptions, not feature allocations. Root App/MainWindow, project/solution and app.manifest retain conventional tool names. Explicit project items separate app code from tests. The latest authorized reset removes only the inventoried legacy graph; no mass renaming is authorized. Each approved feature README must explain its actual folders/files, their responsibilities, pairings, and exceptions as they are introduced. Keep every source file small and focused.
