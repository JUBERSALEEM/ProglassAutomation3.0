# 00 — Project rules: authoritative naming specification

Read [AGENTS.md](../AGENTS.md) first. This document owns naming; the [registry](06.Feature-Registry.md) owns allocation and the [roadmap](04.Project-Roadmap.md) owns phase gates.

## Allocation and scope

- Every application-owned feature root begins with its unique sequential `stepN` identifier and an approved descriptive name.
- `step1` is Theme Studio. `step2` is Client Management (owner approval 2026-10-27, `inquiries.db` migration 1011). On **2026-10-27** the owner established the remaining implementation order and allocated `step3`–`step11` in it: User Management, Company Profile, Project Records & Inquiry Integration (foundation; `step3` was authorized and implemented on 2026-10-27, `step4` and `step5` were authorized and implemented on 2026-10-28), then Proforma Invoice, Job Order, Delivery Note, Tax Invoice, Statement and Reports (blocked by gate `G1`). The order, the gate and the boundaries live in [the business-module roadmap](11.Business-Module-Roadmap.md); allocation is not authorization. Never reuse a number, including after retirement; retain retired entries in the registry.
- Allocate the next unused feature number only after explicit owner approval of its name and scope; record approval evidence and update the registry, roadmap, and feature README together. Never invent future features.
- Unexpected unnumbered application files must be reported by exact path and require clarification before modification/deletion; their origin must not be assumed, and they are not a precedent for new V3.0 features. Shared application-owned concerns need an approved allocation/placement decision, not an invented unnumbered feature.

## Hierarchy

A child inherits its complete parent's identifier and adds one segment. At the feature root, use alphabetic siblings (`a`, `b`, `c`); within such a branch use numeric siblings (`1`, `2`, `3`), and continue with numeric segments only if necessary. Allocate sibling identifiers distinctly within the parent. The same prefix may identify a folder and its descendants, but do not assign the same sibling identifier to unrelated files/folders. Keep structures shallow and purposeful; do not build an empty tree.

### Feature-identifier convention (decided 2026-10-27)

## WPF layout, spacing and accessibility rules (permanent, decided 2026-10-27)

These are project rules: they bind every contributor and every agent, and apply to every WPF view in this repository — existing and future, every module, every theme. They exist because the owner had to report the same three defects (buttons touching each other, controls overlapping, cramped and misaligned forms) one round at a time. A rule that only lives in a chat message is not a rule; a rule that is not checked is not enforced. So each rule below names how it is enforced as well as what it means.

### A. No overlapping controls

* Every control occupies its own region of a layout panel. Nothing may be drawn on top of a sibling.
* `Canvas`, `Canvas.Left/Top`, absolute positioning, `RenderTransform` offsets and negative margins are not permitted for layout. Use `Grid` (with explicit row/column definitions), `DockPanel`, or a `StackPanel`/`WrapPanel` whose orientation matches the flow.
* A horizontal `StackPanel` inside a `*` column is a known overflow source: it never shrinks below its content. Use a `WrapPanel` where wrapping is acceptable, or divide the content into rows/columns that cannot exceed their cell.
* Controls that float over the shell (overlay buttons, `Panel.ZIndex` chrome) are one of the two causes of the sidebar/content collision. Shell actions belong in the region that owns them.
* A XAML file must also **load**. `Style.BasedOn` and `Binding.Converter` are plain CLR properties, not dependency properties: `BasedOn="{DynamicResource ...}"` and `Converter={DynamicResource ...}` throw `XamlParseException` inside `InitializeComponent()`, so an app that compiles cleanly still fails to open. Use `StaticResource` for both, or move the token onto the element (`Style="{DynamicResource Caption}"`) and drive visibility with one `BooleanToVisibilityConverter`. A mistyped `StaticResource` key fails at parse time for the same reason — a missing token is fixed by defining it, never by switching to `DynamicResource`, which fails silently and leaves the property at its default.
* Enforced by: `Theme/step1.d.tests/step1.d.17.XamlPropertyChecks.py` (attribute review) and the layout checks in each module's source checks (for example `step3.f.2`).

### B. Consistent spacing through shared tokens

* Related controls **8**, separate groups **16**, form sections **20–24**, main content padding **24**.
* Button internal horizontal padding **14–18**; minimum interactive control height **36**.
* **Gap between adjacent controls is 16 px, and it has its own tokens.** This
  paragraph used to allow 8–12 px between action buttons. Measured against a
  36–40 px pill, 8 px reads as two controls touching, which is exactly what the
  owner reported on the Company page (round 30b): the row was spaced with
  `MarginInline` — a **text** token (8 px right, 4 px bottom) that also pushed the
  row 2 px off centre. One token was doing two jobs, and its number was wrong for
  the job it was doing. There are now two, one per anchoring:
  * `UiGapControl` (16 px **right**) for a left-anchored row;
  * `UiGapControlEnd` (16 px **left**) for a right-anchored row, so the last
    control stays flush with the card edge instead of floating 16 px inside it.
  * `UiGapFieldInline` (16 px **left**, 12 px bottom) for a field that follows
    another field in the same `Grid` row. A `Grid` has **no** gap property, so
    two, three or six star columns place their boxes edge to edge; `MarginSection`
    (`0,0,0,12`) only sets the row rhythm and never a gutter. The first field in
    a row keeps `MarginSection`; every field after it carries this token.
    (Owner's arrows on the Company form, round 32: Representative↔Mobile,
    Telephone↔Website, Bank name↔Account number, Company name↔TRN.)
  Every clickable surface or chip in a horizontal row carries the row's token;
  `MarginInline` is never used on a button, a radio button, a check box or a chip.
  A new row type (fields, image+text, button+label) needs its gutter audited on
  its own: separating buttons does not separate fields.
* These are design tokens, not numbers to retype. Use the contract tokens `UiGapField`, `UiGapFieldInline`, `UiGapGroup`, `UiGapSection`, `UiGapAction`, `UiGapCluster`, `UiPagePadding`, `UiCardPadding`, `UiActionMinHeight`, `UiActionPadding` (declared in `Theme/step1.a.ThemeEngine/step1.a.1.ThemeContract.cs` and defined in all eighteen theme dictionaries).
* A spacing or size literal typed into an element is a defect even when it happens to look right.
* Cards and plates on the same page share **one** inner inset. `Card`
  (`PaddingCard`) and `Plate` (`PaddingPlate`) are themed separately and do not
  agree — measured 8–24 px across the nine packages — so a page that mixes them
  pins `UiCardPadding` on every one of its cards and pins nothing else; the cards
  then line up with the same left and right edges in all nine themes. This is the
  only permitted override of a themed card's padding.
 Theme-level metrics belong in a theme dictionary; layout gaps belong to the shared tokens above.
* Enforced by: `step1.d.3.verify_sources.py` (every `{DynamicResource …}` in a view must be a contract token) and `step1.d.5`/`step1.d.6` (nine packages, both modes, identical token sets).

* Enforced by: `Theme/step1.d.tests/step1.d.18.LayoutSpacingChecks.py` — every
  theme declares both tokens with the same value, neither side is under 12 px, no
  clickable surface is spaced with the text token, and every surface inside a
  horizontal `StackPanel`/`WrapPanel` carries the token its row's anchor calls
  for. Grandfathered screens (Theme Studio, Inquiry) are frozen at their current
  counts and may get better, never worse.

### C. Responsive layout

* Layouts must reflow, not break: `Auto` for content-sized regions, `*` for the region that absorbs remaining space, `WrapPanel` for rows whose children may not fit.
* No fixed sizes that stop a layout from adapting. A fixed width is acceptable only for a control whose content has a known bound (an icon, a badge, a filter dropdown), and even then the surrounding layout must wrap or scroll.
* Long forms and long lists scroll **inside their own region**. A scroll region must never be replaced by a taller card.
* Every view must remain usable at the supported minimum window size (`WindowMinWidth`/`WindowMinHeight` in the theme contract) with the navigation sidebar both expanded and collapsed.

### C2. Registers (list pages) use the shared pattern, and only it

* Every register is `<DataGrid Style="{StaticResource ListGrid}">` with plain
  `Header="…"` strings and `ElementStyle="{StaticResource ListText}"` (or
  `ListMonoText` / `ListStrongText`) per text column. That is the whole
  configuration; the pattern is defined once in each theme package.
* **Every style reference in a register is `StaticResource`.** A
  `DynamicResource` that has not resolved does not fail — it renders the
  framework default, which is left-aligned, unbolded and untrimmed. The
  register's own setters still use `DynamicResource` tokens, so a theme switch
  repaints.
* **The band draws its own heading label** — `Text="{TemplateBinding Content}"`,
  `HorizontalAlignment="Stretch"`, `TextAlignment="Center"`,
  `FontWeight="{DynamicResource FontWeightHeading}"`. A `ContentPresenter` bound
  to `HorizontalContentAlignment` centres the *box*, not the text, and leaves
  the weight to what the header inherits; round 51's centred band came back
  left-aligned and light in round 53 while every setter looked correct.
* **A style setter is not a rendered glyph.** Before claiming a visual fix, say
  which element renders it — the `TextBlock`, the template, the presenter — and
  check *that*. Three rounds in a row passed source review and failed on screen.
* **The header band is bold, centred and ruled; the body has no grid lines and
  is centred.** Owner, round 50: "column section top panel heading should be
  bold in grid line and center aligned. list related text should not have grid
  line but professionally spacing and center aligned."
* **Every column takes an equal share of the width.** A column never sets
  `Width`: a pixel count is a guess, and the guesses had already clipped the
  project timestamps and the inquiry numbers. A value that does not fit trims,
  and a hover shows it in full — the value style carries
  `list:TruncatedTextToolTip.Enabled`, which measures the text and only opens a
  tooltip when the cell actually cut it off.
* **A page never defines its own `DataGridCell`, `DataGridColumnHeader`,
  `DataGridRow` or cell-text style,** and never overrides `CellStyle` /
  `ColumnHeaderStyle`. Five modules did, five copies drifted, and every fix had
  to be made five times.
* **Nothing sets `StaysOpen` on the hover bubble.** The bubble is assigned to the
  `ToolTip` property, so WPF's `PopupControlService` owns its lifecycle; a
  `ToolTip` element there with `StaysOpen="False"` makes the service throw
  `NotSupportedException` on the dispatcher — on hover, at the top of the message
  loop, logged FATAL. Round 53 shipped exactly that. `StaysOpen` is for a `Popup`
  you open yourself.
* An **editable entry grid** (the inquiry editor's BOQ lines) is not a register:
  it states `IsReadOnly="False"` and keeps its own column widths. Using the
  register style on one would silently make its cells read-only.
* **`ElementStyle` is a plain CLR property, so it takes `StaticResource`.** A
  `DynamicResource` there is accepted by the parser, ignored at run time, and the
  column silently keeps WPF's default left-aligned `TextBlock` — no error, no
  warning, no log line. It shipped that way in round 51: the headers, the equal
  widths and the missing grid lines all appeared (they hang off `Style`, which is
  a real DependencyProperty) and every cell stayed left-aligned.
* **The hover bubble is a themed `ToolTip` (`ListBubble`)**, not a bare string:
  a string tooltip is drawn by Windows and ignores the theme.
* Enforced by: `Theme/step1.d.tests/step1.d.20.ListPatternChecks.py`, which scans
  **every** module view for registers rather than a hand-kept list, so a new
  module is bound by the rule the day it lands. Seven mutations tested: a page
  dropping the style, a column pinning a width, a theme losing the text style,
  a theme losing the tooltip, a header losing its centring, the equal widths
  being dropped, and an entry grid taking the register style.

### D. Buttons and actions

* Adjacent action buttons are separated by **16 px** — always, through
  `UiGapControl` or `UiGapControlEnd`; adjacent **fields** in one row by 16 px
  through `UiGapFieldInline`. Two buttons that share an edge read as one
  malformed control, and at 8 px they read as sharing one (measured, round 30b).
* Action groups (selection actions, status actions, create actions) are separated by 16 px so the groups are distinguishable.
* The primary action must be immediately identifiable and is the only primary-styled button in a region; destructive actions use the destructive style and never sit flush against the primary one.
* Every action button has a minimum interactive height of 36 px and internal horizontal padding of 14–18 px.
* Button order inside a cluster is: primary → secondary → cancel/dismiss.
* Enforced by: the spacing tokens above plus the module source checks that assert token usage and button order.

### E. Text and content integrity

* No clipped or truncated text without a deliberate `TextTrimming` and a tooltip that reveals the full value.
* No control may escape its container; no row may draw outside its card.
* Empty states are actionable ("no users match this filter — clear the filters"), error states say what failed and what to do, and both are inside the region they describe.
* Nothing critical is hidden behind hover, and no action is reachable only by right-click.
* Every user-visible string comes from the view model or the catalogue, never from a hardcoded literal that could disagree with the stored data.
* A dropdown, filter or input must say what it is for — a visible caption or a
  placeholder — and its closed state must never be blank. A selection that cannot
  be resolved (bound before its list was loaded, say) is a defect, not a cosmetic
  detail: the operator cannot tell what the control does.
* A filter carries a visible **label** ("Department", "Role") and its face carries
  its **selection, and only that**. Four arrangements have been tried: the field name
  printed on the button — "Department: All" (round 20, rejected), the field name
  prefixed onto every row (round 23, rejected the same round — "remove department and
  roles from each dropdowns"), a bare value with no label at all (rejected: the owner
  asked for the word on the control, and it cannot be resolved), and the settled one —
  a label beside the box, the selection on the face, the way the Inquiry toolbar
  labels its status chips. The unfiltered row names what it covers ("All departments",
  "All roles"), a chosen row is the catalogue's own wording verbatim, and
  `AutomationProperties` + the tooltip say what the control does in every state.

### F. Sidebar and navigation integrity

* The navigation sidebar and the content region occupy **separate layout regions** of the shell. Collapsing or expanding the sidebar must never overlap, clip or shift content into a control.
* Content reflows when the sidebar toggles; the content region must not paint over the sidebar column.
* Preserve navigation order, selected-page behaviour and the active theme. A layout fix must not renumber workspaces or change which page opens at startup without an explicit decision.
* Scrolling belongs to the content region, not to the shell.
* A state that blocks the operator (no users, no administrator yet, unreadable
  data) must present the way out of that state on the same screen. Telling someone
  to "ask an administrator" in a directory that has no administrator is the defect
  this rule exists to prevent.

### G. Dialogs, overlays and menus

* A dialog or overlay is sized by its content (with a maximum), centred on the region it blocks, and never so small that its own fields or buttons are clipped.
* An overlay must obscure only what it is blocking; popups and context menus must not cover the control that opened them.
* Keyboard: `Esc` dismisses, focus starts in the first field, focus is trapped inside the overlay while it is open, and focus returns to the invoking control when it closes.

### H. Accessibility

* Readable type at the shipped sizes; contrast is verified by the theme contract (`step1.d.3` measures 1514 contrast pairs).
* Every interactive control is reachable by keyboard, shows a visible focus indicator, and has an accessible name (`AutomationProperties.Name` when the visible text is not sufficient).
* Order in the visual tree is the tab order; nothing important is mouse-only.

### I. Theme compatibility

* Every colour, brush, metric, radius and font comes from the theme contract through `DynamicResource`. No hardcoded colour, no screen-local palette, no `StaticResource` of a theme-owned card role.
* Controls with a theme-owned template bind the implicit style explicitly (`Style="{DynamicResource {x:Type ComboBox}}"`), so a theme switch replaces the template as well as the tokens.
* A layout change must be checked in **all supported themes**, at minimum Light and Dark, because a fix that fits in one density may clip in another.

### J. Required verification before declaring a WPF module complete

Compilation is not layout verification, and reading XAML is not visual verification. Before reporting a module as complete, and before claiming any UI work is finished:

1. Build the project where the tooling exists; fix every error you introduced.
2. Inspect every changed XAML file **and** the shared layout it inherits (shell, sidebar, page padding, card roles).
3. Run the automated source checks: `step1.d.3`, `step1.d.4`, `step1.d.5`, `step1.d.6`, `step1.d.11`, `step1.d.15`, `step1.d.17`, `step1.d.18` (control spacing), `step1.d.19` (file size), plus the module's own checks (`step2.f.2`, `step3.f.2`, `step4.f.2`). Extend a checker when a new defect class is found — a defect fixed without a check is a defect that returns.
4. Verify at the normal size **and** at a smaller supported size, with the sidebar **expanded and collapsed**.
5. Check for overlap, clipping, spacing, alignment, control heights, scrolling and empty/error states in each of those states.
6. Verify Light and Dark wherever a runtime exists.
7. **Report explicitly which visual checks could not be performed**, and why. Never present a source-only inspection, a mock-up or a rendered approximation as evidence of native WPF rendering.

### K. No god files (permanent, decided 2026-10-28)

* Owner instruction: *"never keep any file long like god files, keep them small
  separate parts for the same module, so they are easy to maintain."*
* A C# file is at most **400 lines**. An XAML file is at most **750 lines** — past
  that it stops being readable and has to be split.
* Split by role, not by cutting a file in half: styles go to a
  `ResourceDictionary` the view merges (that is what
  `step4.d.3.CompanyProfileStyles.xaml` is for — the Company page fell from 946
  to 724 lines without one element leaving it); each band of a page and each
  group of commands gets its own part; a large class is split by responsibility
  (`partial` where it is one object).
* A split file keeps its module prefix and its number (`step4.d.3`), so the
  hierarchy still says what it belongs to.
* Files that predate the rule are listed in the checker with their size on
  2026-10-28. They may be split, never grown: a new line in one of them belongs in
  a new part. When one is split below the cap its exemption is deleted — a stale
  exemption is a lie, and the checker fails on it.
* Enforced by: `Theme/step1.d.tests/step1.d.19.FileSizeChecks.py`.

### L. Never ask for the password twice on the same device (permanent, decided 2026-10-28)

* Owner instruction, round 32: *"the app asks for device login repeatedly —
  remember the last login until Sign out."*
* A sign-in on this workstation is remembered in
  `%LOCALAPPDATA%\ProGlassAutomation\device-session.json` and resumed at the
  next launch, so the password is typed **once** per session, not once per start.
* What may be stored: the directory id, the username, the Windows account the
  sign-in was made under, the row's password stamp and a timestamp. **Never** a
  password, a hash, a salt or a token.
* What must refuse to resume: the row is gone, inactive, has no password, must
  change its password, was reset since (the password stamp moved), or the
  Windows account is different. Each of those clears the record instead of
  resuming it.
* One explicit **Sign out** clears it. Nothing else may write or clear the
  record except the shell (`MainWindow`), and no other module may add a second
  login prompt.
* Enforced by: `step3.f.2.UserSourceChecks.py` → `require_session_is_remembered`.

### M. A field row needs a gutter, not just a row gap (permanent, decided 2026-10-28)

* A `Grid` has no gap property. Two, three or six star columns place their
  content edge to edge, and `MarginSection` (`0,0,0,12`) only sets the row
  rhythm — it can never separate two fields **in the same row**.
* The first field in a row keeps `MarginSection`; every field after it carries
  `UiGapFieldInline` (16 px left, 12 px bottom).
* This is the second half of the round-30b lesson: separating buttons does not
  separate fields. Every row type — button row, field row, image + text row — is
  audited on its own.
* Enforced by: `step1.d.18.LayoutSpacingChecks.py` (theme parity for the token,
  plus a per-row check that walks every `Grid` with two or more columns).

### N. One diagnostic log, and it records failures only (permanent, decided 2026-10-28)

* There is exactly **one** technical log: `Diagnostics/AppLog.cs` writing
  `%APPDATA%\ProGlassAutomation\Logs\proglass-errors.log` through
  `AppDataRoot`. No module writes a second log file, no third-party logger is
  added, and `Debug.WriteLine` is not a log (Release compiles it away).
* **Failure only.** A caught exception, a failed write, a failed startup, a
  process-level fault. Never startup, navigation, a successful save, a theme
  change, a heartbeat, a poll, or ordinary validation feedback such as a missing
  company name or a duplicate username.
* **Never business audit.** Who changed which inquiry, client, user or company
  lives in `InquiryCommunications`, `CurrentOperator` and the operator columns.
  The log holds technical failure, not activity.
* **Privacy first.** No password, hash, salt, token, credential, bank number or
  e-mail address is written; `AppLogRedaction` masks by name and by shape, and
  the operation id — never the customer's text — identifies the failure.
* **Defensive.** A logging fault may not throw, recurse, or hide the exception it
  was recording. `AppLog` returns `bool` and keeps the reason in
  `LastWriteFailure`. The folder is created by the first failure, the total size
  is bounded (1 MB × 5), and there is no log unless something failed.
* **A dispatcher fault is not silently absorbed.** An unhandled UI fault is
  recorded, the operator is told, and the application closes through its own
  shutdown path. `Handled = true` is used only so the runtime unwinds into that
  shutdown; it is never used to keep a possibly inconsistent screen alive. Faults
  that a page can actually handle are caught where they happen instead.
* **Honest.** A record proves an exception was observed. It does not prove the
  process survived; a crash on a killed process, a fault before the traps are
  attached, or an OS-level termination can leave nothing behind, and no report
  may claim otherwise.
* Enforced by: `Diagnostics/tests/AppLogSourceChecks.py` (single logger, failure
  only, placement, lazy creation, bounds, defensiveness, redaction, the three
  process traps, severity vocabulary, wiring, the benign case, documentation).
