## 3. Module boundaries — `G1-03`, `G1-04`, `G1-05`

Four cross-module storage accesses exist. Each is a real dependency doing a
legitimate job, and each is currently implemented by reaching into another
module's storage.

### 3.1 Client Management reads `Users` — `G1-03`, **confirmed (3 sites)**

`step2.ClientManagement/step2.b.4.ClientRepository.cs` opens `UserDbContext`
directly at **lines 221, 419 and 439** — to resolve a representative's name, to
list representatives, and to validate a representative assignment.

The dependency is legitimate: a client must name a representative. The defect is
*how* it is satisfied. The draft found one site; there are three.

### 3.2 Company Profile reads `Users` — `G1-04`, **confirmed**

`step4.CompanyProfile/step4.b.4.CompanyProfileRepository.cs:140-152` —
`ResolveUserNameAsync` opens a context and executes
`SELECT "FullName" FROM "Users" WHERE "Id" = @id` as raw SQL. It is used to show
"last saved by" (`step4.c.1.CompanyProfileViewModel.cs:421`).

### 3.3 Project Records writes `Inquiries` — `G1-05`, **confirmed, and already narrow**

`step5.ProjectRecords/step5.b.6.ProjectRepository.Link.cs` — attaching an inquiry
is one parameterised `UPDATE` of one column, guarded in the same statement:

```sql
UPDATE "Inquiries" SET "ProjectRecordId" = $projectId
 WHERE "Id" = $inquiryId
   AND "ProjectRecordId" IS NULL
   AND EXISTS (SELECT 1 FROM "Projects" p WHERE p."Id" = $projectId)
```

It cannot insert or delete an inquiry, cannot rewrite its number, text, status or
timestamps, and cannot move an inquiry between projects without an explicit
detach. The file states this and the SQL matches it. This is the narrowest of the
four and the least alarming — but it is still a write into another module's table,
and the owner must approve the boundary rather than have it inferred.

### 3.4 What the rule actually says

`docs/00.Project-Rules.md` and `docs/11.Business-Module-Roadmap.md` §5 require each
module to own its own storage. Folders are not a boundary. The four accesses above
are the complete set at this revision — that is now enforced by
`Theme/step1.d.tests/step1.d.21.ModuleBoundaryChecks.py`, which fails on any new
one, so the register cannot grow silently between reviews.

**PASS.** The set is known, bounded, documented and gated. What remains is
approval, not discovery.

## 4. Identity and audit attribution — `G1-06`, **confirmed and worse**

### 4.1 Two identity sources, and they are not the same one

| Module | Field | Written from |
| --- | --- | --- |
| `step4` Company Profile | `CreatedByUserId`, `UpdatedByUserId` (integers) | `AuthenticationContext.Current` — the signed-in app user |
| `step3` Users | `CreatedByUserId`, `UpdatedByUserId` | `AuthenticationContext` |
| `step5` Projects | `CreatedBy`, `UpdatedBy` (**`TEXT NOT NULL DEFAULT ''`**, `step5.b.1.ProjectSchema.cs:85-86`) | `CurrentOperator.DisplayName` (`step5.b.4.ProjectRepository.cs:152, 165-166, 223, 251`) |

`CurrentOperator` is not the app session. `Inquiry/Services/Audit/CurrentOperator.cs:27-46`
returns `Environment.UserDomainName\Environment.UserName` — **the Windows
workstation login** — falling back to the literal `"Operator"` when nothing is
resolvable.

So a project created in ProGlass by signed-in user *Juber Saleem* is stamped with
whatever Windows account the machine is logged in as. On a shared or generic
workstation account ("Reception\PC", "Admin"), every project ever created records
the same name, and a rename in Users cannot resolve it.

This is not merely "text instead of IDs". It is a **different identity domain**.

### 4.2 The fields named in the draft

`PreparedBy`, `CheckedBy`, `IssuedBy` do not exist yet — no transaction document
is implemented. This review cannot certify fields that are not written. What it can
say is that the mechanism for correct attribution already exists
(`AuthenticationContext`, `UserSession`, `CaptureStampAsync`) and that **step5 does
not use it**.

### 4.3 Required before acceptance

1. Decide the attribution model: stable user id + name-at-time-of-action snapshot,
   or id alone with names resolved at read.
2. Migrate `step5` to it (a new migration on the same chain; `CreatedBy`/`UpdatedBy`
   as text cannot be silently reinterpreted).
3. Decide how an inactive or renamed user appears in an old record.
4. State the rule for future documents in `docs/12` so `step6` inherits it.

**BLOCKED ON AN OWNER DECISION.** This is a design choice about the product's
audit trail, not a defect I should quietly patch.

## 5. Permissions — `G1-07`, **confirmed and sharpened**

Four separate controls, measured per module at this revision:

| Module | Authentication | Authorization (writes) | Read scope | Attribution |
| --- | --- | --- | --- | --- |
| `step3` Users | repository-wide session gate; every user has a password (PBKDF2-HMAC-SHA256, per-user salt, fixed-time compare) | **Administrator enforced in the repository** (`step3.b.4.UserRepository.cs:154, 475, 831, 865, 913, 940`); last active Administrator protected (`:272, 923`) | a non-administrator sees their own row only | `AuthenticationContext` |
| `step4` Company Profile | via the session gate | **Administrator enforced in the repository** (`step4.b.4.CompanyProfileRepository.cs:172-176`: actor must be active *and* an administrator) | single installation row | `AuthenticationContext` |
| `step2` Clients | via the session gate | **NONE.** `CreateAsync` (`:283`), `UpdateAsync` (`:329`) and `SetActiveAsync` (`:376`) contain validation and a representative check, and **no role check** | yes — a non-administrator's query is scoped to their own representative id (`:147-148`, `step2.c.2.ClientWorkspaceViewModel.cs:296-298`) | `AuthenticationContext` |
| `step5` Projects | via the session gate | **NONE, at any layer.** The repository has no role concept; `CanEditSelected` is selection state only (`step5.c.1.ProjectWorkspaceViewModel.cs:208`) | all projects | **the Windows login** (§4) |

Two corrections to the draft:

- the draft described `step2` as having "query-level read scoping ... but the
  reviewed write paths do not establish a comparable module-wide role policy".
  It is stronger than that: **there is no authorization on the client write paths
  at all**;
- the draft did not mention `step5` has no authorization anywhere, not even a UI
  gate.

A hidden button is not authorization. Today, anyone who can reach the client or
project view model can write through its repository.

**NOT READY FOR ACCEPTANCE.** The owner must decide what each role may do —
`docs/11` §4 forbids inventing a permission matrix for rights that have not been
approved, and that prohibition stands.

## 10. Verdict

**G1: NOT ACCEPTED.** Not because the foundation is weak — the migration design,
the identity work in `step3`/`step4` and the list pattern are sound — but because
four questions are the owner's to answer, and one piece of evidence cannot be
produced in this environment:

**Decisions needed (owner):**

1. **Audit attribution** — user id + name snapshot, or id resolved at read? Until
   this is settled, `step5` writes the wrong identity (`G1-06`), and every
   transaction document would inherit the mistake.
2. **Permission policy** — which roles may create/edit clients and projects? Today
   neither is guarded at the repository (`G1-07`).
3. **Cross-module boundary** — approve the four accesses as they stand, or require
   a user-directory contract and a linking service (`G1-03/04/05`).
4. **`step5` test coverage** — authorise a behaviour-test project (`G1-08`).

**Evidence still to be produced (owner's machine, not this one):**

5. `dotnet build`, launch, sign in; open Clients, Users, Company, Projects.
6. Upgrade a **backed-up copy** of a real `inquiries.db`; compare inquiry counts and
   historical values; confirm `PRAGMA user_version` = 1017.
7. Nine themes × Light/Dark, one screen each, recorded as owner-run evidence.

**What is already green:** 16/16 source checkers, four mutation harnesses all
caught, nine themes registered with full token parity in both modes, and the
round-51–55 list pattern now defined once per package and gated.

**`step6` Proforma Invoice is not authorised by this document.** It starts when the
owner accepts G1 — and it inherits decision 1 and decision 2 above, because a PI
carries `PreparedBy`/`CheckedBy`/`IssuedBy` and is written by someone who must be
allowed to write it.
