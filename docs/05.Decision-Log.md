## 2026-10-27 — `step3` User Management: authorization is enforced in the write path, and identity comes from the workstation account

**Authorized scope.** User Management only: users, departments, roles, activation,
permission-guarded administration, and the attribution identity future documents
will use. Company Profile, Project Records, Inquiry integration, PI, JO, DN, TI,
Statement and Reports were explicitly excluded, as was any unrelated theme or
module redesign.

**Decision 1 — no login, no password, no second identity system.**
The application has no credentialed login: the only operator identity that exists
is `Inquiry/Services/Audit/CurrentOperator.cs` (the Windows workstation account),
used today for `PreparedByName`, `UploadedBy` and `AcknowledgedBy`. The stage
therefore resolves the current user by matching that account name to a user row,
and stores **no** password, hash, salt or token. Adding a password box would have
been a fabricated security feature with nothing behind it. If the company ever
wants genuine application-level sign-in, that is a separate, explicitly approved
decision with its own credential store.

**Decision 2 — permission is enforced below the UI.**
Every write resolves the operator inside its own transaction and refuses when the
operator is unidentified, inactive or not an Administrator. The window disables
buttons as a courtesy, but a caller that bypasses the view model is refused just
the same. The last-active-Administrator guard reads its count in the same
transaction, so two windows cannot demote each other out of existence.

**Decision 3 — departments and roles are catalogues, not enums.**
The owner required that a department can be added later without a redesign. A
seeded table with a stable code and a renameable display name achieves that with an
insert; an enum would require a rebuild and a migration. A department remains an
organisational fact and is never consulted as a permission; role is the only
authorization input, and only for the rules actually approved.

**Decision 4 — no invented permission matrix.**
Accountant, Salesman, Estimator, Foreman, Cutting Department and Double Glazing
Department have no per-module rights in this stage. The modules those rights would
govern do not exist yet (they start at `step6`, after gate `G1`). Inventing a grid
now would create requirements nobody approved and would have to be undone later.

**Decision 5 — attribution stores an id and a snapshot, never a typed name.**
A prepared record carries the stable user id plus the name and role as they were at
signing time. Looking a name up at render time would silently rewrite history when
a person is renamed; storing only a typed name would lose the link to the person.
Both are avoided. In this stage the pattern is exercised by
`Users.CreatedByUserId` / `UpdatedByUserId`, which are ids rendered through a
lookup.

**Decision 6 — the client representative reference stays deferred.**
`step2` reserved `Clients.RepresentativeUserId` for the User Management stage. The
owner scoped this round to User Management only and did not authorize changes to
the Clients screen, so the reference is **not** added. When approved it is a
nullable `RepresentativeUserId` column in a later migration plus one selector in
the client editor; existing client rows stay valid and unassigned. Recorded here so
the dependency is not lost.

**Verification state.** Portable source checks pass; the C# behaviour executable
and migration 1013 have been written but not compiled in this environment. Windows
build, WPF runtime and nine-theme Light/Dark rendering remain unverified by the
agent; the owner's MSBuild is the only compiler.

## Round 24 — a password, a session, and a read scope

**Instruction (owner, 2026-10-27):** *"there should be a password so normal user
should not be able to create admin account etc or each users should have password…
but user should have password so user should be able to read the data related to
them only."* This reverses the earlier position — recorded in this log and in
`step3.a.1` — that the application would have no credential at all and take its
identity from the Windows account.

**Decision 1 — every user has a password, and only that password identifies them.**
`step3.a.5.UserPassword` owns the whole mechanism: PBKDF2-HMAC-SHA256, 210 000
iterations, a 16-byte per-row salt, a 32-byte hash and `CryptographicOperations.
FixedTimeEquals` for the comparison. Migration **1015** adds the columns; existing
rows keep working and simply have no credential until an administrator sets one
(`SignInCode.NoPassword` says exactly that). Nothing is stored in plaintext, nothing
is reversible, and no password is written to a log or shown on a screen.

*Why not a hand-rolled hash, why these numbers:* a password hash is the one place
where "it works" is not the question — it has to resist offline guessing. The
platform's PBKDF2 is audited, and the parameters are stored **with the row**, so the
cost can be raised later without invalidating anybody's password.

**Decision 2 — the session, not the Windows account, is the operator.**
`step3.b.7.AuthenticationContext` holds the signed-in row and is the only thing
`UserRepository.CurrentOperatorUsername()` reads. It is set by a verified sign-in
and cleared on sign-out, so every authorization decision — "may this person manage
users", "may this person attribute a document" — is asked of a password-verified
identity. Before sign-in the username is `""`, which matches no row, so every write
refuses. The Windows account is still used, but only for what it is good for: the
first-run bootstrap, where nobody exists yet to sign in as.

**Decision 3 — a temporary password must be replaced before the session starts.**
An administrator who resets somebody's password sets `MustChangePassword`; the same
sign-in card then asks for a new one and only hands the session over afterwards.
Resetting *yourself* never sets the flag, because you already know the credential you
just chose. Changing your own password requires the current one, refused **before**
any write when it is missing — a check that could be bypassed by leaving the field
blank would be decoration.

**Decision 4 — the read scope is a property of the query, applied as a ceiling.**
A signed-in non-administrator reads their own user row and only the clients they
represent, and the inquiries they are the salesman or preparer of; an Administrator
reads everything. The ceiling is applied first, before any scope the caller asks for,
so a page cannot widen it by passing a different id,
and the register's status counts are narrowed by the same query so the chips cannot
reveal how many people exist. The workspace still passes the id explicitly: the
intent is visible where the query is built, and the two layers agree.

**Decision 5 — a filter says which field it filters, from outside the rows.** Fourth
and final arrangement for the department/role boxes: a visible label to the left
("Department", "Role"), the selection alone on the face ("All departments" / "All
roles", then the catalogue's own wording). The word inside the face of every row was
tried this round and reverted — in a field of seven values it reads as a placeholder
and doubles the word in "Cutting Department". All four arrangements are now listed in
`AGENTS.md` rule E.

**Verification state.** Nine portable checkers PASS. `step3.f.2` gained
`require_credential_policy` (PBKDF2, constant time, no plaintext column, gate under

## Round 25 — the app must load, not only compile

**What the owner saw.** The rebuilt application closed at start-up with

```
System.Windows.Markup.XamlParseException
  at ProGlassAutomation.MainWindow.InitializeComponent()
A 'DynamicResourceExtension' cannot be set on the 'BasedOn' property of type 'Style'.
A 'DynamicResourceExtension' can only be set on a DependencyProperty of a DependencyObject.
```

**Decision 1 — `BasedOn` takes `StaticResource` or nothing.**
`Style.BasedOn` is an ordinary CLR property on `Style`; it is not a dependency
property, so `DynamicResource` cannot be assigned to it. The XAML compiler accepts
the markup, the key exists in every theme dictionary, and the file parses — the
error appears only when the parser builds the style at run time, which is why the
build was green and the window never appeared. Two views carried the pattern
(`step3.d.1`'s read-scope note and `step3.d.2`'s password-state note), both written
during the password round. They now use the shared token on the element
(`Style="{DynamicResource Caption}"`) and a `BooleanToVisibilityConverter`
(`x:Key="UserVisibility"`, the house pattern already used by `BoolVis`) for the
show/hide. The same rule governs `Binding.Converter`: a converter is not a
dependency property either.

**Decision 2 — a missing `StaticResource` key is a crash, so it is a checker.**
`DynamicResource` is forgiving and silent: an unknown key leaves the property at its
default. `StaticResource` is not — an unknown key throws while parsing. That
asymmetry is now enforced by `step1.d.17`, which gained three rules and lost one
narrowness:

* (1c) `DynamicResource` on a non-dependency property (`BasedOn`, `Converter`),
  reported with the file and line;
* (1d) a `StaticResource` key that resolves in neither the file, nor a theme
  dictionary, nor `App.xaml`;
* (1e) a `Style`-typed attribute pointed at a key that is not a `Style` — aiming
  `Style` at a brush key throws when the property is set;
* (1f) a style applied to a type it does not target — a `TextBlock` style on a
  `Button`, or a `TextBlock` style passed as the DataGrid's `CellStyle`;
* (1g) a style derived with `BasedOn` from a style that targets a different type;
* the `DynamicResource`-key rule now scans **all** XAML files, not the three views
  it was written for.

**Decision 3 — the checker reads code, not documentation.** A rule that forbids a
pattern will be quoted in the comment that explains the fix. Every rule now runs on
comment-blanked text (`code_only()`), keeping line numbers intact, so the note above
the fix cannot fail the fix's own gate.

**Decision 4 — the rule is written where the next person will look.** `AGENTS.md`
and `docs/00.Project-Rules.md` now state that a XAML file must also *load*, that
`BasedOn`/`Converter` take `StaticResource`, and that a missing token is fixed by
defining it — never by switching to `DynamicResource`, which fails silently.

## Round 26 — the first boot that already has users

**The owner's question.** *"first boot how can have a password when until now there
was no password in username. are you blindly applying fixes?"*

**The answer, for a fresh installation.** The password does not exist before the
first boot — it is chosen **on** it. The first-run card shows the Windows account
this workstation already runs under (read, not typed), asks for a full name, a
department, and a password twice, and the row is created with that password in the
same write. So the row never exists without a way to sign in as it, and the sign-in
gate that follows asks for the password that was just chosen. Nothing is seeded,
nothing is blank, and no default password exists anywhere in the codebase.

**The gap the question exposed.** There is a *second* first boot: the owner's own
database. It already has users — created by earlier builds, before migration 1015 —
and 1015 deliberately kept every row and gave none of them a password. In that state
`SignInAsync` refused every account with *"This account has no password yet. Ask an
administrator to set one"*, and no administrator could sign in to set one. That is
the same circular instruction the first-run gate exists to prevent, one version
later, and it would have greeted every existing installation on its first launch
after this round. It is fair criticism: the credential round was checked against an
empty database and not against an upgraded one.

**Decision 1 — sign-in tells the two cases apart.** A row with no credential still
cannot be signed into (no blank-password door, ever). The message now depends on the
directory: if some account has a password, `"Sign in as an Administrator and set one
on this page"`; if **none** does, it says so plainly, because there is no
administrator who could be asked.

**Decision 2 — one door, and it is narrow.** `SetFirstPasswordAsync` sets the first
password and closes the moment it would stop being true:

| Guard | Why |
| --- | --- |
| Refused when **any** row has a password | it can never be used to take over an installation that already has credentials |
| The row is resolved from the workstation account **inside** the write transaction | it cannot be aimed at another person's row; there is no `userId` parameter to pass |
| The row must be **active** and an **Administrator** | a normal user's row cannot be claimed at the machine, which is exactly the escalation the owner ruled out |
| The password is **not** temporary | the person chose it; there is nobody above them to force a change |

**Decision 3 — both surfaces ask the same question.** The startup gate and the Users
page card are the same step (`IFirstRunService`), and both hide the name and
department fields in this state: giving an existing row a way in must not be a way to
change who somebody is. When the workstation does not match the administrator row, the
card names the account to run from instead of failing silently.

**Decision 4 — the page asks for the sign-in gate.** Setting the password from the
Users page happens with no session (that page is reachable when the gate was
dismissed), so the write is followed by `AuthenticationContext.RequestSignIn()` and the
shell shows the gate. `SignedOut` cannot carry this: it only fires when a session
ended, and "sign out" would be a lie when nobody ever signed in.

**Evidence.** `step3.f.2` gained `require_first_password_upgrade()` — the refusal, the
directory-aware message, the one-shot guard, the workstation-resolved row, the

## Round 27 — a write that reported success and stored nothing

**What the owner saw.** The first-password card from round 26, with this message above
it:

```
The password was written, but the directory now reports 0 account(s) with a password.
Sign in with the one you just set; if that fails, report this message.
```

That sentence is the verification step added in round 26 doing its job: the write had
returned success and stored nothing, and the check said so instead of the operator
discovering it at the sign-in screen.

**Cause.** `UserRepository.FindUserRowAsync` loads the row with `AsNoTracking()`. It is
a *read* helper — correct for `FindCurrentUserAsync`, `ResolveDisplayNameAsync` and the
sign-in lookup — but `SetFirstPasswordAsync` used it for a row it then modified. EF
tracks nothing, `SaveChangesAsync` reports 0 rows, nothing is written, and the method
returns `Ok`. The same helper was already being used that way by `SignInAsync`, which
mutates `FailedSignInCount` and `LockedUntilUtc`: **the 5-attempt lockout never
persisted**. Five wrong passwords locked nothing — a security defect in the round-24
credential work, not only in the new card.

**Decision 1 — writes get their own lookup.** `FindUserRowTrackedAsync` is the tracked
row for anything that will be saved; `FindUserRowAsync` keeps its no-tracking query and
now says, where it is defined, that its rows must never be handed to a write path.
`SignInAsync` and `SetFirstPasswordAsync` use the tracked one.

**Decision 2 — a silent write is impossible from here on.** `RequireTracked(db, target,
operation)` throws when the context is not tracking the row, and every password write
(the first password, a self-change, an administrator reset) keeps the affected-row count
`SaveChangesAsync` returns and refuses to report success when it is zero. The failure
becomes a message, not a password that does not work.

**Decision 3 — the check is one rule, not two cases.** `step3.f.2` gained
`require_writes_are_tracked()`: the two lookups must both exist and the read-only one
must document its restriction; sign-in and the first-password step must use the tracked
lookup and must not use the read-only one; and the number of password writes must equal
the number of tracked guards and the number of affected-row checks. Removing any one of
the three from any one write fails the gate. Six mutations were put back on purpose and
each failed with its own message.

**Decision 4 — behaviour is read back from the database.** `step3.f.1` now signs in once
with a wrong password and re-reads the row to require `FailedSignInCount == 1`, then
exhausts the attempts and requires `LockedUntilUtc` in the future and the *correct*
password refused with `Locked`. The lockout is proven, not assumed.

**Decision 5 — two pieces of noise the same screenshot exposed.** The yellow banner
"This workstation account is not registered as a user, so user management is
unavailable. Ask an administrator…" was printed directly above the card that registers
that account: a directory where nobody has a password has no session by definition, so
the refusal is now suppressed while either first-run card is showing (it returns the
moment an account can sign in). The register's "No user matches the current search and
filters." was likewise hidden while a first-run card is up — with the card showing, an
empty register is the expected state, not news.

**Not verified here.** No .NET SDK in this environment: `step3.f.1` (including the new
lockout checks) must be run on Windows, and the card is the owner's to try again.

`CREATE TABLE IF NOT EXISTS`, no seed row (so "never saved" stays distinguishable
from "saved empty"), no Inquiry/Client/User row or column touched, no second
database and no second runner.

**Decision 3 — the logo is a file NAME inside the app data folder.** ADV stored
the picker's absolute path; that breaks the moment the data folder moves or a
backup is restored beside another installation. Here a picked image is copied to
`%APPDATA%\ProGlassAutomation\CompanyProfile\logo-<guid>.<ext>` and only that
generated name is stored, so a profile travels with its artwork. It is copied to
a temporary name and moved into place, so no row can ever point at a half-written
file, and the asset that a save replaced is deleted **only after the commit** — a
failed save leaves the stored profile and its logo exactly as they were.

**Decision 4 — one logo dimension, and both placements are real compositions.**
ADV stored width and height in millimetres separately, which is precisely how a
logo gets stretched. This module stores ONE value (the long edge, 8–80 mm) and
derives the other from the image's aspect ratio; every `<Image>` in the view is
`Stretch="Uniform"`. `LeftPortrait` (mark beside the identity) and `TopPanel`
(full-width masthead with a rule beneath) are previewed as two different
compositions of the same identity, so the choice is visible rather than two
words in a list. A placement with no logo behind it is refused; a stored logo
with the text-only placement is allowed, because "keep the artwork on file, print
text only" is a real letterhead choice, not an error.

**Decision 5 — one validation implementation, called twice.** `step4.a.2` runs
in the editor before the write and again in the repository before it persists, so
a caller cannot skip it. The UAE TRN is optional, exactly 15 digits when present,
and separators are stripped rather than refused. Nothing optional was made
mandatory: a name-only profile saves.

**Decision 6 — the write is authorised in the repository.** `SaveAsync` reads
`AuthenticationContext.Current` (set only by a verified password, round 24) and
requires an active Administrator; the refusal is a returned message, not a greyed
button. The write path loads a **tracked** row — round 27's defect was a
no-tracking row accepting assignments and storing nothing — and treats an
affected-row count below 1 as a failure, so a save cannot report success while
writing nothing.

**Decision 7 — a read path for the documents that do not exist yet.**
`GetIdentityAsync()` returns an immutable `CompanyIdentitySnapshot`. Step6+ will
read that instead of copying company fields into their own tables. Nothing from
step5+ was scaffolded: no numbering, no VAT, no currency, no PDF, no PI/JO/DN/TI.

**Decision 8 — the page is a settings page, in the Settings group of the rail.**
Workspace index 10 (every earlier index keeps its meaning), one command bar that
wraps, four named sections, stacked labels that survive a narrow window, one
vertical scroll region with horizontal scrolling disabled, per-field messages and
a sentence above them, an unsaved-changes line in words, and a read-only notice
that prints the reason. Every colour, metric, radius and font is a theme-contract
key; the controls that carry theme-owned templates (`TextBox`, `ComboBox`) bind
the active implicit style; nothing is a literal and no theme package was edited.

**A defect found while writing the checker.** The editor raised
`"LogoSizeMmError"` while the page binds `LogoSizeError`, so a size message would
have been stored and never shown. `RaiseFieldError` now maps the persisted field
name to the property the page binds, and the static gate requires every message
binding the view uses to exist on the view model.

**Verification — what was actually done.** `python3` ran the nine existing
portable checkers plus the new `step4.f.2` (mutation-tested: the guard, the
constraint, the delete-after-commit ordering, the tracked write and the bindings
were each broken on purpose and the gate failed with its own message).
**Not done, and not claimed:** this environment has no .NET SDK and no WPF
runtime, so nothing was compiled, `step4.f.1` was not executed, the window was
not opened, and no theme was visually verified. Those remain the owner's to run
on Windows.

## 2026-10-28 — Round 28a: the two errors the owner's compiler found

**What the owner saw.** Visual Studio, on the build I could not run:

```
CS0103  step4.c.1.CompanyProfileViewModel.cs:85   The name 'LoadAsync' does not exist in the current context
CS0103  step4.c.1.CompanyProfileViewModel.cs:148  The name 'UserCatalog' does not exist in the current context
```

**Cause 1 — the command pointed at a method that was renamed.** The constructor
wired `RefreshCommand` to `LoadAsync`, while the method is `ReloadAsync`: the
method was renamed during round 28 and the one call site was missed. A stale name
is invisible to every source check that looks for *presence*.

**Cause 2 — a type used without its namespace.** `UserCatalog` lives in
`ProGlassAutomation.Models.Users` (step3.a.2), not in `...Services.Users`. The
repository already imported both; the view model imported only the services
namespace, so `UserCatalog.IsAdministrator` did not resolve.

**Fix.** `RefreshCommand` calls `ReloadAsync`; the view model imports
`ProGlassAutomation.Models.Users`.

**Why the gate let them through, and what changed.** `step4.f.2` checked that
*filenames*, *tokens*, *constraints* and *bindings* exist, but never that the C#
itself names things that exist — and there is no compiler in the authoring
environment, so nothing else could have caught it. Two rules were added:

* `require_calls_resolve()` — every unqualified `await X(...)` and every method
  wired into a `DelegateCommand` lambda must be declared in that view model. This
  is exactly the `LoadAsync` defect.
* `require_cross_namespace_imports()` — a table of the module's cross-namespace
  types (`User`, `UserCatalog`, `AuthenticationContext`, the company model and
  services, the database helpers) plus the rule that a file using one must import
  its namespace. This is exactly the `UserCatalog` defect.

Three mutations were put back on purpose — the `LoadAsync` call, the missing
`using` in the view model, and the missing `using` in the repository — and each
failed with its own message. Two false positives the rules produced on their
first run were fixed rather than tolerated: a *folder name* (`"CompanyProfile"`)
is not a type reference, and an *event* wired into a command is a declaration.

**Not claimed.** Still no .NET SDK here: the fix is verified by the static gate
and by reading, not by a build. The owner's rebuild is the authority.
