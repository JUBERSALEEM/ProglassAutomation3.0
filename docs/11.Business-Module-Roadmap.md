## 2. Feature-identifier convention (decided 2026-10-27)

- **One sequential number per approved feature.** `step1`, `step2`, then
  `step3`, `step4`, … allocated in the order above. The number identifies the
  feature for its whole life; it is never reused, including after retirement.
- **Dotted sub-identifiers are not feature identifiers.** Labels such as
  `step2.1`, `step2.2`, `step2.3`, `step2.4` do **not** exist in this repository
  and must not be created. The same applies to `step3.1` and onward. Ordering is
  expressed by the allocated number, never by a dotted variant of another
  feature's number. (This preserves the standing rule recorded in the decision
  log on 2026-10-27 that "`STEP 2.1` is not a repository identifier" and turns it
  into a general convention rather than a one-off remark.)
- **Inside a feature, the existing hierarchy applies**: `stepN.a`/`b`/`c` for
  alphabetic children, `stepN.a.1` for numbered grandchildren, per
  [Project Rules](00.Project-Rules.md).
- **Theme positions never allocate feature numbers.** The nine-theme order is a
  visual roadmap, not a feature sequence.
- **Allocation is not authorization.** A number in the registry means "this
  module, this name, this place in the order". It does not authorize writing the
  module; each foundation module needs its own owner approval, and every
  transaction module additionally waits for gate `G1`.

## 3. Gate `G1` — Foundation Review

`G1` is the boundary between foundation/master-data work and transaction
documents. It is a review, not a development stage: it produces a checklist and
an evidence-based acceptance report, and it produces **no** feature code.

It reviews `step2`–`step5` together and must cover at least:

1. **Migrations and existing data** — one chain, `PRAGMA user_version`, backup
   before migrate, one-transaction apply, post-migration verification, and proof
   that existing Inquiry rows and their historical text snapshots are unchanged.
2. **Module boundaries** — each module owns its own tables, rules and views; no
   module reaching into another's storage layer; client records, user identity
   and company configuration remain separate concepts.
3. **Identity references** — how a client representative, `PreparedBy`,
   `CheckedBy`, `IssuedBy` and comparable audit fields resolve to a user, and
   whether any existing placeholder column is being repurposed (it must not be,
   without an approved design).
4. **Permissions** — what roles exist, what each may do, and where enforcement
   actually happens.
5. **Tests and evidence** — automated checks for each module, plus the honest
   statement of what could not be run here (Windows build, WPF runtime) and what
   the owner ran manually.
6. **Theme compatibility** — all nine installed themes in Light and Dark, at
   least by token/style coverage checks, with any rendered verification recorded
   as owner-run evidence rather than claimed by the agent.

`G1` is accepted when the owner accepts that report. Until then `step6`–`step11`
are not started, not scaffolded and not "prepared" in code.

## 5. Rules that bind every module in this sequence

- **List pages** follow [10.List-Page-Pattern](10.List-Page-Pattern.md): one
  command bar, state in dropdowns, collapsible filters, register to the bottom.
- **One database file, one migration chain.** A module adds its version(s) to the
  existing chain in `AppSchemaMigrations`; it never creates a second chain, a
  second file, or an inline `ALTER TABLE` outside the runner.
- **Existing Inquiry data is immutable without an approved design.** No
  repurposing of `CustomerId`, `ProjectId`, `SalesmanId`, `PreparedByUserId`, and
  no matching historical rows to clients by name.
- **Themes are consumed, never modified.** Modules use contract tokens and the
  contract's control styles; no module edits a theme package.
- **Verification honesty.** Portable checks are what this environment can run.
  Windows build, WPF runtime and rendered visual acceptance are reported as not
  run until the owner runs them and says so.
- **One focused commit per change**, with the registry, roadmap and feature
  README updated in the same change that alters status.

## 6. What is not authorized by this document

No module starts because it is listed here. This document records the order and
the gate; implementation authority comes from a separate, explicit owner approval
per module. Nothing here allocates a theme, a database file, a dependency, a
release or a workflow change.
