# 18 — Migration preservation report (G1-02)

**Question:** does the migration chain, including 1017, preserve existing Inquiry
data?

**Revision:** `da65a9e` + this change.
**Status: NOT RUN — the migration has not been executed against a real database.**

That is the honest headline and nothing below contradicts it. This document
contains (a) what could be proved from source without executing anything, (b) a
ready-to-run harness that produces the missing evidence on the owner's machine in
one command, and (c) the exact table to fill in when it has been run.

---

## 1. Why it was not run here

The migration is C# (`SchemaMigrationRunner` + `AppSchemaMigrations`), it targets a
Windows WPF application's SQLite file, and this environment has **no .NET SDK and
no Windows**:

```
$ dotnet --version
dotnet: command not found
```

Two further facts make a substitute impossible rather than merely inconvenient:

- **The database is not here.** It lives at
  `%APPDATA%\ProGlassAutomation\inquiries.db` on the owner's machine. There is no
  copy in this repository, and no legacy `.db` fixture was ever stored in it.
- **A re-implementation would not be evidence.** The exact SQL could be retyped
  into a Python script and run here, but that would test my transcription of the
  migration, not the migration. The question asked is about the application's own
  runner, so only that runner counts.

The one thing this environment *can* do — and did — is read the chain's code and
prove that it contains no statement capable of destroying an inquiry row, and that
the runner's guards are in the order claimed. That is §4. It is a different claim
from "data survived", and it is labelled as such.

## 3. The safe procedure (one command, nothing in production touched)

### 3a. Which checkout to run it from — read this first

The repository has three remote branches, and its **default** branch is
`ThemeStudio-9`, which does not contain `tools\` or `step5.f` at all:

| Branch | Contains this procedure? |
| --- | --- |
| `ThemeStudio-9` (default — what a plain `git clone` checks out) | **no** |
| `arena/da841e06-proglassautomation3-0` (earlier session branch) | no |
| `arena/81baffde-proglassautomation3-0` (this work) | **yes** |

So a plain `git clone` produces exactly the error "`tools\Verify-Migration1017.ps1`
does not exist". That is not a missing file — it is a missing branch.

**The safest way to get it, without disturbing the checkout you work in**, is a
second working tree. Run these in the folder where your repository is cloned:

```powershell
git fetch origin arena/81baffde-proglassautomation3-0
git worktree add D:\G1\repo origin/arena/81baffde-proglassautomation3-0
```

`D:\G1\repo` is then a complete checkout of the branch with the procedure, and
your current branch, your uncommitted work and your files are untouched. When you
are done, `git worktree remove D:\G1\repo` deletes only that second checkout.

(If you are already on `arena/81baffde-proglassautomation3-0`, skip this — just run
`git pull` and confirm that `dir tools` lists `Verify-Migration1017.ps1`.)

### 3b. The command

The application already supports being pointed at another folder — the same hook
its own tests use (`AppDataRoot.TestFolderOverride`, `step2.f.1.ClientRuleChecks.cs:309`).
So **no configuration file and no source change is needed**, and the production
path is never passed to the runner.

On the Windows machine, in the checkout from 3a, with the application **closed**:

```powershell
cd D:\G1\repo
powershell -ExecutionPolicy Bypass -File "$PWD\tools\Verify-Migration1017.ps1" -Destination D:\G1
```

`$PWD` matters: PowerShell's `-File` resolves a relative path against whatever
folder the console happens to be in, so a relative `tools\…` fails silently the
moment that folder is not the repository root. The absolute form above cannot make
that mistake. If the path is still wrong the script now says so explicitly, and its
first lines record the repository folder, branch and commit in the log.

What it does, in order:

1. Finds `%APPDATA%\ProGlassAutomation\inquiries.db` and prints its size and
   timestamp. It is only ever **read** by `Copy-Item`.
2. Stops if the application is running (a copy taken mid-write could be
   inconsistent), and warns if a `-wal` file exists.
3. Creates `D:\G1\G1-migration-<timestamp>\` containing
   - `frozen\inquiries.db` — the archive; never opened again,
   - `working\inquiries.db` — the copy the migration is applied to.
4. Proves both copies exist **and** match the original by SHA-256 before anything
   else happens.
5. Runs `step5.f.2` against the **working copy only**. That tool resolves the
   production path itself and refuses it outright, independently of the script.
6. Leaves everything in place and prints the report path.

If the copy is already at 1017 — which it will be if the application has been run
since the module landed — the tool prints `NOT RUN` and explains why. Add
`-Rewind` to make the upgrade real:

```powershell
powershell -ExecutionPolicy Bypass -File "$PWD\tools\Verify-Migration1017.ps1" -Destination D:\G1 -Rewind
```

`-Rewind` removes **only what 1017 created** (the `Projects` table, its five
indexes, the `ClientId` and `ProjectRecordId` columns) and sets `user_version` back
to 1016 — **on the copy**. It refuses if any project row or any linked inquiry
exists, because removing those objects would destroy data. It then re-checks that
the inquiry rows are byte-identical after the rewind before letting the migration
run, so a rewind can never be the thing that changed the data.

## 6. Documented schema changes to expect (not failures)

If the copy is older than the current model, migrations 1001–1016 run before 1017
and some of them **intentionally change the schema**. These are recorded here so a
difference is not mistaken for corruption:

| Migration | Change | Treatment |
| --- | --- | --- |
| 1001 | converges any legacy shape: `CREATE TABLE IF NOT EXISTS`, one `ADD COLUMN` per missing column | additive |
| 1002 | **drops** legacy Inquiry columns (`InquiryDate` and friends) not in the model | documented removal — the harness fails it **only** if the dropped column still held values |
| 1004, 1005, 1007, 1009 | add `RowVersion`, website-inbox and acknowledgement columns | additive |
| 1006, 1010 | rename/restore inquiry child tables to the mapped names | structure only, no inquiry rows |
| 1011–1016 | Clients, Users, Company Profile | new tables |
| 1017 | `Projects` + two nullable link columns + indexes | additive |

Since the application has been in use on this machine, the copy is most likely at
1017 already, in which case **only** 1017 is pending — the fully additive case. The
`-Rewind` path exercises exactly that one migration.

## 7. How to read the result

Run the command in §3, then open
`D:\G1\G1-migration-<timestamp>\working\inquiries.db.g1-migration-report.md`.

- **Exit code 0** and `PASS: the migration preserved every inquiry record, every
  value and every legacy column` → the required evidence exists.
- **Exit code 1** → a check failed; the report names which, and
  `frozen\inquiries.db` is the untouched original. Nothing needs to be restored:
  production was never opened.
- **Exit code 3** → the copy was already current; re-run with `-Rewind`.
- **Exit code 2** → refused (production path, missing file, app running, or rewind
  inappropriate). Nothing was changed.

Paste the report back and the result can be entered into
[17.Gate-G1-Foundation-Review](17.Gate-G1-Foundation-Review.md) §2 as evidence, or
recorded as a failure — either way it stops being an assumption.
