## 2. Where the database is and how 1017 is applied

| Item | Value |
| --- | --- |
| Data folder | `%APPDATA%\ProGlassAutomation` (`AppDataRoot.ProductionFolder`) |
| Database file | `…\inquiries.db` (`InquiryDbContext.DatabaseFilePath`) |
| Chain tip | **1017** (`AppSchemaMigrations.Inquiries.Max(m => m.Version)`) |
| Registration | `AppSchemaMigrations.cs:234` — `new(ProjectSchema.MigrationVersion, …)` |
| Implementation | `step5.ProjectRecords/step5.b.1.ProjectSchema.cs` → `Ensure` |
| Applied by | `SchemaMigrationRunner.Upgrade`, called from `InquiryRepository.InitializeAsync` (`InquiryRepository.cs:49`) at application start |

`Upgrade` does, in this order: read `user_version` → compute the pending set → **make
a backup** (SQLite online-backup API + `quick_check`, refuse if it cannot) → open one
transaction → apply every pending migration → re-run every migration's `Verify` →
`PRAGMA quick_check` → set `user_version` → commit. A failure rolls the transaction
back and leaves `user_version` where it was.

The harness calls `SchemaMigrationRunner.Upgrade` **directly** rather than starting
the application, because application start calls `Database.EnsureCreatedAsync` first,
which builds the current model and would mask exactly the upgrade being tested.

## 4. Can `-Rewind` reverse 1017 safely? — audited, not assumed

The rewind is only acceptable if it removes **exactly** those eight objects and
nothing else. It does, and the claim is enforced three ways:

| 1017 object | How the rewind removes it |
| --- | --- |
| Table `Projects` | `DROP TABLE IF EXISTS "Projects"` — also removes `IX_Projects_Number` |
| `IX_Projects_ClientId`, `IX_Projects_Status_Name` | `DROP INDEX IF EXISTS` (explicit, before the table) |
| `IX_Inquiries_ClientId_Step5`, `IX_Inquiries_ProjectRecordId` | `DROP INDEX IF EXISTS` — **must** go first, because SQLite refuses to drop an indexed column |
| `Inquiries.ClientId`, `Inquiries.ProjectRecordId` | `ALTER TABLE "Inquiries" DROP COLUMN` each, only if present |
| `user_version = 1017` | set back to 1016 (the highest registered version below 1017) |

Three independent proofs, because a rewind that removes too little would silently
become the "before" side and make the whole comparison meaningless:

1. **Refusal on data.** `Rewind1017` first counts project rows and linked inquiries.
   If either is non-zero it refuses and changes nothing — removing those objects
   would destroy data. Nothing is "cleaned up" to make the test run.
2. **Self-check on the rows.** Before any DDL it takes a fingerprint over the
   columns that will *survive*; after the rewind it takes the same fingerprint again
   and refuses to continue if the rows changed. A rewind cannot be the thing that
   altered the data.
3. **Object-by-object shape comparison in the harness.** After the rewind the tool
   recomputes the schema and asserts, one object at a time, that *table set = at-1017
   minus `Projects`*, *index set = at-1017 minus `IX_Projects_*` and the two inquiry
   link indexes*, *Inquiries column list = at-1017 minus the two link columns*, and
   *`user_version` = 1016*. Any leftover fails the run.

`step1.d.22` now pins this: the drop list is parsed from 1017's own source, so a
future column added to 1017 without a corresponding drop fails the checker. Nine
deliberate breakages of these rules (rewind stops dropping a column, stops dropping
an index, harness stops comparing the table set, probe removed, script copies
production again, …) are all caught.

One honest limitation: the rewind rebuilds the table physically, so the rewound file
is not byte-identical to a database that never had 1017. It is *logically* identical
for the columns that pre-date 1017, which is what the test needs, and the harness
proves that rather than assuming it.

## 9. Limits of this evidence, stated plainly

- **One inquiry row.** The copy held a single record. That exercises the migration
  on real data but says nothing broad about legacy variety — different historical
  shapes are covered by the chain's own convergent migrations, not by this run.
- **Not the production upgrade.** The real upgrade happens the next time the
  application starts, on the real file, with the runner's own backup. This proves the
  code is safe to do that; it does not exempt that launch from keeping
  `MigrationBackups`.
- **No UI, no concurrency.** The test runs with the application closed, on one
  machine (`AppDataRoot` is single-station by design).
- **`-Rewind` is a test instrument, not a supported rollback.** It exists so a
  current database can be taken back one step *on a disposable copy*; it is not
  offered to users and it refuses whenever data would be lost.
