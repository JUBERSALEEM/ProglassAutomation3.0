## Phase 01 acceptance criteria

- Actual native WPF Theme Studio, not an image/browser substitute, within the approved step1 hierarchy; no ERP/business workflows.
- A documented typed semantic contract covering applicable colors/surfaces, shape/spacing, typography, depth/effects and interaction/status states, with complete isolated Bento Light/Dark visual packages, including Bento-owned component styles/templates; shared infrastructure remains non-visual.
- Centralized runtime switching bound to actual active state; existing elements, representative controls and open dialogs update coherently without restart. No disconnected preview system, per-card recoloring, fake options or stale references.
- Required samples, reusable analytics and an optional semantic-resource diagnostics view per the [feature specification](../step1.ThemeStudio/step1.c.docs/step1.c.1.ThemeStudio-README.md).
- Development/tests detect missing or incompatible mandatory tokens; switching/resource replacement and safe failure behavior are tested. Future-theme addition is documented without screen rewrites or speculative themes.
- Actual solution builds successfully using the configured supported toolchain; introduced errors fixed and pre-existing failures distinguished. Applicable focused automated tests pass with execution evidence.
- Actual WPF runtime verification: both appearances, existing-element updates, buttons/inputs/selections/panels/status states, keyboard/focus, contrast, resizing at multiple supported sizes/scales, longer text and performance. Compilation alone is insufficient. Unavailable runtime checks remain explicitly incomplete.
- Review finds no unexplained hardcoded theme styling, copied component definitions, unauthorized dependencies/features or unrelated edits; every permitted exception is documented narrowly.
- Theme code follows the permanent Theme directory architecture, with shared engine/resources separate from stable named individual theme folders and no empty future-theme trees. Placement deviations need documented technical reasons and advance approval.
- Full research → specification → implementation → build → runtime inspection → comparison → correction → regression verification → user review evidence is recorded. Actual source URLs and WPF adaptations, real Light/Dark palette and component specification precede implementation. Correct inconsistencies at shared-resource/component level and rerun checks; a generic palette alone is not completion.
- Completion report follows [AGENTS.md](../AGENTS.md), docs/registry show actual status, and owner approves the result. Do not call incomplete/unverified coverage complete.

**Stop after Phase 01** and await approval before implementing any later theme or feature. Finishing step1 does not authorize step2.
