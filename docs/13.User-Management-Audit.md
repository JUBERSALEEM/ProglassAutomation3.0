## 4. The owner-reported defects, and their causes

### 4.1 A dropdown with no face

**Symptom:** the department and role boxes rendered with no text on the button.

**Cause:** `SelectedValue` bound to a code string. The list is filled later, and a
`SelectedValue` that cannot be resolved at the moment it is applied leaves the
control unselected; nothing re-applies it afterwards, so the box keeps an empty
face forever. This is a mechanism, not a styling detail — no amount of colour or
padding fixes it.

**Fix, applied to every catalogue picker in the module** (both register filters, the
editor's department and role, the first-run card, and the shell's start-up gate):

* the control binds **the row object** (`SelectedItem` / `SelectedItem`-style
  properties on the view model), so there is no code→item lookup to fail;
* each view model points its property at a real row **after** the catalogue loads
  (`_selectedDepartmentFilterItem = DepartmentFilters[0];` and the equivalents);
* a stored code that is no longer in the catalogue gets a row of its own, labelled
  `"<code> (not in the catalogue)"`, instead of a blank face.

**Face wording (round 24, fourth and final arrangement):** a visible label sits to
the left of each box ("Department", "Role") — the Inquiry toolbar's arrangement —
and the face shows its *selection*: "All departments" / "All roles" when nothing is
filtered, then the catalogue's own wording ("Cutting Department", "Estimator"). The
three earlier arrangements (caption beside the box only, field word inside the face
of every row, bare value with no label at all) are recorded as rejected in
`AGENTS.md` rule E; the label is what makes the box say which field it filters
without putting the word inside the rows.

### 4.2 The representative could not be edited

**Symptom:** "clients representative have no edit support".

**Cause:** the picker listed only active users **with the Salesman role**. The
reference was already written on update as well as on create, but for a client whose
representative was anybody else the list had no row to show, so the box fell back to
"No representative" — reading as a field that cannot be edited — and the next save
would have cleared the assignment.

**Fix:**

* the list is now **every active user**, salesmen sorted first, so a business with no
  salesman yet can still record who owns a client;
* the picker binds the row and is seeded from the client's stored
  `RepresentativeUserId` in the constructor, so opening an existing client shows its
  representative and saving it unchanged keeps that id;
* a stored reference whose user is no longer active gets an explicit
  `"(inactive)"` row (`EnsureRepresentativeOption`) — added, never silently replaced
  or dropped.

### 4.3 Identity is a password, and the scope follows the person

**Owner instruction (2026-10-27):** *"there should be a password so normal user
should not be able to create admin account etc or each users should have password…
but user should have password so user should be able to read the data related to
them only."*

**What changed.** The Windows account is no longer the identity; it is only what the
first-run bootstrap registers. A user row now carries a password that the person
chose, and `AuthenticationContext` — set by a verified sign-in and cleared on sign
out — is the identity every write resolves.

| Concern | Decision | Where |
| --- | --- | --- |
| Storage | PBKDF2-HMAC-SHA256, 210 000 iterations, 16-byte salt, 32-byte hash, `FixedTimeEquals`; no plaintext, no reversible encoding | `step3.a.5.UserPassword.cs`, migration 1015 |
| Policy | 8–128 characters, at least one letter and one digit; the same rule on every screen | `step3.a.3.UserRules.ValidatePassword` |
| Sign-in | Username + password; unknown user, wrong password (with attempts left) and inactive are three different sentences; 5 failures lock the account for 60 s | `step3.b.4.SignInAsync`, `step3.c.4`, `step3.d.4` |
| A password an administrator set | `MustChangePassword = true`, replaced on the sign-in card before the session is handed over | `step3.b.4.ResetPasswordAsync` |
| Changing your own password | Requires the current password, refused before any write when it is missing or wrong | `step3.b.4.ChangePasswordAsync`, `step3.c.1` |
| Creating an administrator | Only an active Administrator can create or edit users, refused in the repository, so a normal user cannot mint an Administrator row from any screen | `step3.a.4`, `step3.b.4` |
| Reading other people's data | The query applies a ceiling first: a signed-in non-administrator reads only their own user row, the clients they represent, and the inquiries they are the salesman or preparer of. An Administrator reads everything. A signed-out process reads nothing through the app because no page is reachable. | `step3.b.4.QueryAsync`, `step2.b.4.QueryAsync`, `Inquiry/Services/Inquiry/InquiryRepository` |

**What it does not claim.** There is no password strength meter, no expiry, no
history, no two-factor authentication and no recovery by email. The lockout is in
memory and resets with the process. Nothing here was compiled or run — see §2.5.

### 4.4 Card placement

The bar and the register card are siblings on the page padding, and both pin the same
inset (`UiCardPadding`, 16 px in all eighteen theme dictionaries), so their contents
start on the same vertical line in all nine themes. Two leaks were closed this round:
the register's `DataGrid` no longer carries `MarginItem` (4/8/10 px depending on
theme, which changed the card's bottom inset per theme), and the editor's action
footer is a **hairline rule** instead of a `Plate` nested inside the `Card` (the
inner surface carried `PaddingPlate` while the card carried `UiCardPadding`, so the
buttons sat a few pixels in from the fields — in every theme).

**Reversed by the owner in round 24, recorded so it is not re-argued:** the earlier
"no password / no login" position. Identity is now a credential, and the Windows
account is only what the first-run bootstrap registers.
