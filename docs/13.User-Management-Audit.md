## 4. Defects found and fixed in this round

1. **Cards did not share an inset.** Root cause measured, not guessed: `Card`
   ships `PaddingCard` (8/12/16/20/24 across the nine packages) and `Plate` ships
   `PaddingPlate` (8/12/14/16). The bar is a `Plate` and the register is a `Card`,
   so the table started a few pixels right of the search box, differently in every
   theme. Every page-level card in `step3` now pins `UiCardPadding` (16 in all
   eighteen dictionaries), and `step3.f.2` fails if a new card does not.
2. **A field name was printed on the filter buttons** (`Department: All`). The
   owner rejected that. The faces now carry the selection only — "All departments"
   / "All roles" before a choice, then the catalogue's own wording — with no caption
   beside the box. `step3.f.2` fails on a reintroduced prefix or caption.
3. **A one-item overflow menu.** The command bar's "⋯" held only Refresh, so the
   only way to reload was two clicks on a mystery control. It is now a named
   Refresh button; the bar may not use a `ContextMenu` at all.
4. **The editor card did not line up** either: it carried an extra
   `PaddingCompact` margin and a doubled inner padding. It now starts on the page
   padding and uses the same card inset as the register.
5. **CS0246 on the owner's build:** `step3.c.3.FirstRunViewModel` used
   `DelegateCommand` without its namespace. Fixed, and `step3.f.2` now fails any
   step3 file that constructs the type without importing it.

## 4b. Round 22 — the deferred item, built

The client's representative was the only item on the deferred list. It is now a
**reference, not a text column**:

* migration **1014** adds `Clients.RepresentativeUserId` (`INTEGER NULL`) plus its
  index, registered on the one chain **after** 1013 so the table it points at
  always exists; existing client rows are untouched and stay valid;
* the migration's verify step fails the upgrade if any stored reference names no
  user, and refuses a zero or negative id;
* the client editor gained one picker (active users with the Salesman role, read
  from `UserCatalog.SalesmanRole`), with "No representative" as a real choice and a
  hint — not a dead dropdown — when no salesman exists yet;
* the client register gained a Representative column that shows the **resolved
  name**; a rename relabels the register without rewriting a client row;
* the write path refuses an id that names no user, so an orphan cannot be created;
* a deactivated salesman disappears from the picker while the clients that already
  reference them keep their stored id — history is not rewritten by a status change.

Behaviour coverage for this lives in `step2.f.1` (rules, projection, and a
repository round-trip that assigns, renames, clears and deactivates through an
isolated database) and source coverage in `step2.f.2`.

## 5. Open gaps, honestly ranked

| # | Gap | Impact | Suggested handling |
| --- | --- | --- | --- |
| 1 | **Username hygiene.** The editor accepts any username; a row created for an account that does not exist on the workstation (`JuberSaleem` in the screenshot) can never operate the app, and it looks like a duplicate person next to `MALIK\DELL`. | Medium — confusing data, unreachable identity. | Warn (do not block) when the typed username does not contain `DOMAIN\`, and show the workstation account as the suggested value. |
| 2 | **No column sorting.** `CanUserSortColumns="False"`; the list is ordered by the repository only. | Low–medium — with a few dozen users this is fine, with hundreds it is not. | Enable sorting on Name / Department / Role / Updated with a stable sort key in the query. |
| 3 | **Search does not match display wording for two catalogues.** It matches stored codes, so "Cutting Department" does not find the row whose code is `CUTTING`. | Low. | Join the catalogues in the query, or search against both code and display name. |
| 4 | **No audit history table.** Only `CreatedByUserId` / `UpdatedByUserId` are stored; earlier versions of a row are not kept. | Low for now; becomes relevant when company documents must be traced. | Decide with `step4`/documents whether an append-only change log is required. |
| 5 | **No pagination.** Every row is loaded. | None at current scale. | Revisit when the register passes a few hundred rows. |
| 6 | **No CSV export / bulk actions.** | None stated in scope. | Only if the owner asks. |
| 7 | **The nine themes have not been eyeballed** with this layout in Light and Dark. | Medium — theme-specific spacing regressions are exactly what rounds 16–18 kept finding. | Owner pass; the token rules make the layout identical, but rendering can still surprise. |

  theme-independent, but that is a claim about source, not a sighting.

  states, error states, the read-only state and the inactive badges are not in it.
