### 1.3 The database change — migration **1017**

```sql
CREATE TABLE "Projects" ( Id, ProjectNumber TEXT(32) UNIQUE, ProjectName TEXT(200),
    ClientId INTEGER NULL → Clients(Id), ClientName TEXT(200) snapshot,
    Location TEXT(200), Description TEXT(1000), Status TEXT(16) CHECK IN ('Active','Closed'),
    CreatedAt, CreatedBy, UpdatedAt, UpdatedBy );
CREATE UNIQUE INDEX IX_Projects_Number; CREATE INDEX IX_Projects_ClientId;
CREATE INDEX IX_Projects_Status_Name;
ALTER TABLE "Inquiries" ADD COLUMN "ClientId"        INTEGER NULL;  -- no default
ALTER TABLE "Inquiries" ADD COLUMN "ProjectRecordId" INTEGER NULL;  -- no default
```

Rules the schema enforces: purely additive; no backfill; no name matching; the
legacy `CustomerId` / `ProjectId` / `SalesmanId` / `PreparedByUserId` placeholders
are never written, read, renamed or dropped (`AssertShape` re-checks the first two
still exist after migrating); attaching an inquiry is **one guarded `UPDATE`**
(`SET ProjectRecordId … WHERE Id = $i AND ProjectRecordId IS NULL AND EXISTS(project)`)
— no `INSERT`, no steal, and the inquiry's `UpdatedAt` is not touched.

## Part 2 — What we got

### 2.1 A capability, not a diff

The application now has a **twelfth workspace, Projects**, where an operator can:

- create a project for a client, or for nobody (**NO CLIENT**) with a typed
  name — the one-off-customer path is untouched;
- see every project with its number, client, site, status and **how many
  inquiries are filed under it** — a project with zero inquiries still appears;
- filter by All / Active / Closed and search number, name, client and site;
- close and reopen a project — **never delete one**;
- **file an existing inquiry under a project** and take it back out, from the
  project's own panel, without opening or editing the inquiry.

### 2.2 What did not change — and that is the deliverable

| Guarantee | How it is held |
| --- | --- |
| Existing inquiries keep their text and their dates | the module never writes `Inquiries` except `ProjectRecordId`; the attach statement does not touch `UpdatedAt` |
| No historical inquiry is guessed at | two new columns are `NULL` on every existing row; a gate rule fails on any name comparison |
| The four legacy placeholder columns survive | asserted by `AssertShape` after every migration, and by the gate |
| A closed project keeps its number and its inquiries | numbering from `max + 1`; no delete path exists |
| Deactivating a client does not orphan a project | `ClientId` is never nulled by client status; the stored client name is a snapshot |
| Free text still works | `ClientId` is nullable by design |

## Part 5 — What cannot be claimed

Stated plainly, because the difference matters:

1. **Nothing was compiled.** No `dotnet`. "It builds" is a judgement from
   syntax and API reading, not a result.
2. **Nothing was rendered.** No Windows, no WPF. The Project page has never been
   seen by anyone, in any theme.
3. **Migration 1017 has never run against a database.** Not the owner's, not an
   empty one. Whether SQLite accepts the DDL on an existing file is untested.

   have an `f.1 …Checks.cs` console project; `step5.f` has only the portable
   gate. This is a real gap against the pattern established by its siblings —

## Part 7 — What was *not* built, deliberately

Project costing, budgets, profitability, time or material allocation, a project
document chain, moving inquiry ownership, a join table (one inquiry → one
project), a project picker on the inquiry editor, automatic backfill, name
matching, and any delete path. Each is excluded in `docs/12` and enforced by
`step5.f.1` where it can be.
