## Bento Grid / Modular direction

Professional modern industrial desktop design: meaningful modular panels, consistent alignment/spacing, deliberate information hierarchy, readable typography, practical grouping, restrained borders/elevation, consistent controls, efficient space, and clear status/interaction states. Do not make every element a floating card. Design Light and Dark deliberately; do not derive one by indiscriminate color inversion. No Claymorphism styling as the primary appearance.

## Semantic resource contract — authoritative specification

This is the required contract **policy**, not generated resources or a finalized key/type manifest. During approved implementation, document every mandatory key, its exact WPF type, meaning, component consumers, allowed values, and coverage in both Bento appearances in the feature documentation. Keep the manifest small but complete for actual controls; represent inapplicable categories explicitly rather than hiding missing resources. No empty future-theme dictionaries.

| Category | Required roles, as applicable | Semantic examples |
| --- | --- | --- |
| Colors and surfaces | Application background; primary/secondary/elevated surfaces; cards/panels; primary/secondary/muted text; primary/secondary accents; borders/dividers/outlines; focus; hover/pressed/selected/disabled; success/warning/error/information; overlays/transparency | `SurfacePrimary`, `SurfaceElevated`, `TextPrimary`, `TextMuted`, `BorderSubtle`, `AccentPrimary`, `StatusError` |
| Shape, sizing and spacing | Card/control radii; button/input dimensions; spacing scale; padding; panel gaps/grid spacing; alignment/layout measurements owned by the system | `SpacingMedium`, `CardCornerRadius`, `ControlMinHeight`, `ContentPadding` |
| Typography | Font families/fallback, sizes, weights; heading hierarchy; body; labels/captions/helper text; contrast/readability requirements | `FontFamilyBody`, `FontSizeHeading`, `FontWeightLabel` |
| Depth and effects | Elevation/shadows, edge treatment, layering, opacity/transparency, supported theme effects | `ElevationPanel`, `BorderThicknessControl`, `OverlayOpacity` |

Choose exact resource types against real WPF consumers (for example brushes vs colors, scalar spacing vs Thickness). Names must describe meaning, not an incidental hue such as `BlueCard`. Use complete replaceable theme packages with theme-owned appearance dictionaries and reusable styles/templates. “Reusable” means shared by application consumers, not a global visual implementation shared by different themes. Resource scope and load order must be documented; duplicate keys within a scope and undefined references are defects. Complete Light and Dark sets must satisfy the same mandatory typed keys.

### No screen-local theme styling

Prohibit theme-owned hardcoded hex/RGB values, local foreground/background/border brushes, duplicate shadows, radii, repeated typography, copied button/input styles, per-view Light/Dark values, one-off state colors, scattered code-behind recoloring, and independent card themes. Centralized token definitions necessarily contain concrete values; consumers must use the contract instead of copying them.

### Card insets and new-module guard

A card's theme-owned `PaddingCard`/`PaddingPlate` is the canonical inset between its border/effect and its content. In product pages, apply the active theme role directly (`DynamicResource Card`, `Plate`, `HeroCard`, etc.) and use the container `Margin` for space between cards. Do not replace a card's padding with `PaddingCompact`/`PaddingControl`, or create a view-local `*CompactCard` style based on `StaticResource Card`; those shortcuts make text hug the card edge and can capture a stale theme style when the active dictionary is replaced. If a workflow truly needs denser insets, define and validate a theme-owned semantic variant in every implemented theme rather than shrinking one screen locally. Regression checks must cover card insets and live style lookup across current themes so future modules inherit the rule.

Only genuinely data-specific colors/visualization encodings or exceptional elements that cannot reasonably consume shared tokens may differ. Document each exception, reason, owner/location, exact scope, and contrast/accessibility implications in the feature README. Keep exceptions narrow. Phase 01 exceptions and platform-owned boundaries are recorded in the feature README. Preserved source outside explicit project items is not claimed compliant or part of the new UI.

### Entire component tree must be theme-aware

Each theme’s reusable styles/templates must consume its own contract resources for all applicable states: normal, hover, pressed, selected, disabled, keyboard-focus, validation/error, loading, and empty states. Coverage includes windows/content, cards/tiles/panels, buttons/icon buttons, text/numeric inputs, combo/selection controls, checkboxes/radios/toggles, tables/lists/headers/rows, menus/dropdowns/context menus, dialogs/confirmations, tooltips/helper messages, scrollbars/separators, and status indicators. Apply this requirement as controls are introduced; it does not authorize implementing all these controls in Phase 01. Verify default templates and popup resource scopes rather than assuming platform defaults satisfy it. Custom templates must preserve behavior, required named parts, focus, and theme responsiveness.

### Only standard WPF APIs — no invented properties, enum values, or resources

Permanent rule (owner-directed, after the first Windows build of the Inquiry module): **anything that does not exist in the standard WPF framework must not be included or implemented in this repository’s code.**

- Every XAML property, attribute, enum value, and attached property must exist in standard WPF (`System.Windows`) for the target framework (`net8.0-windows`), verified against the WPF reference before it is written. Plausible-sounding but non-existent names are defects — real incident: `IsSortable` does not exist on `DataGridColumn` (the real property is `CanUserSort`); it aborted markup compilation and cascaded into a storm of spurious designer errors (`XLS0414`, `XDG-0001`, `XDG0005`, `XDG0008`) that masked the real cause.
- Every `{DynamicResource}` / `{StaticResource}` key must resolve to a resource defined in the active theme package or in the file’s own `Resources` at the moment the reference is introduced (not "later"). Undefined references are defects.
- C# string literals must be exact: embed quotes with escaped regular strings (`"\""`); use raw string literals (`"""`) only deliberately and always confirm the closing delimiter; statements may never appear inside expressions (real incident: `?? return Fail(...)` — `CS1525`). Corrupted quote escapes produce unterminated raw strings (`CS8997`) of the same defect class.
- **Verification gate before committing any XAML/C# change:** (1) every property/enum value used is checked against the WPF API surface; (2) a string-literal integrity scan runs over all touched files (balanced regular/verbatim/raw strings and char literals); (3) for a brand-new module, the first actual Windows build is a mandatory gate — errors reported by the owner’s build are treated as authoritative, fixed, and counted in the completion report. Designer-only diagnostics that disappear once the real compile errors are fixed are cascade noise and are reported as such, not "fixed".

## Genuine runtime switching

Use one centralized application-wide theme/appearance mechanism. Bento Light/Dark are complete variants, not background presets. The selector binds to actual active state; Theme Studio's samples and token reference use the same live application resources. Switching must update existing windows/elements, shared controls, templates and open dialogs consistently without restart, per-card handlers, or manual screen edits. No second preview palette or nonfunctional future-theme choices.

Validate both semantic roles and required style WPF target types using the candidate package alone; reject duplicates across merged files rather than depending on override order. Prefer a verified WPF whole-package replacement and binding strategy for mutable resources. Use appropriate dynamic references for replaceable values; static references are only suitable where identity is intentionally invariant and verified. Verify resource types, nested style/template references, merge precedence, binding/property-change behavior, and popup/dialog lookup. Do not assume that every DynamicResource or StaticResource usage automatically achieves full runtime coverage. Validate a complete set before application; define and test safe failure behavior so incomplete resources do not leave a mixed/broken appearance.

## Adding a future theme — required repeatable process

Only after separate authorization:
1. Record the theme's roadmap position and approved scope; theme order is not a new feature allocation. Use its stable directory under Theme and keep only non-visual orchestration/contracts in the shared engine, with every visual style/template inside its owning theme.
2. Supply complete Light and Dark variants of the existing typed semantic contract, plus its own complete compatible styles/templates and visual treatments. Do not inherit Bento or borrow another theme’s visual system. No copied views or replacement application controls.
3. Run key/type/completeness checks for each variant and tests that deliberately omit or mistype a required resource. Missing mandatory resources must be detected during development/testing, not silently become broken UI.
4. Register the theme in the centralized mechanism only when functional; test replacement against existing screens, controls, open dialogs, and all relevant states. Do not add theme-name branches to screens or edit unrelated business logic.
5. Verify build, accessibility, layout, performance and rendered behavior; document any contract extension and owner approval. Existing screens must continue consuming semantic resources without rewrites.

The engine and typed contract now exist; this extension procedure remains subject to build/runtime verification and separately authorized future-theme work. Phase 01 must demonstrate the reusable contract with Bento Light/Dark only; it must not implement a second theme to claim extensibility.

## Layout, accessibility and performance

- Use WPF content sizing, suitable panels, proportional/auto grid definitions, sensible minimums and shared spacing; avoid fixed dimensions that unnecessarily prevent adaptation. Verify resizing, supported display sizes, Windows scaling/DPI, longer text/font differences, and switching at multiple sizes. No clipping, overlap, unreadable labels, unnecessary horizontal scrolling, lost controls, or lost content.
- Establish readable heading/body/caption roles and licensed/available fonts with fallback. Exact token values, supported sizes/DPI and performance budgets require review, not assumptions. No unsupported letter-spacing hacks.
- Target at least 4.5:1 ordinary text contrast, 3:1 large text and essential non-text indicators. Measure actual combinations in both appearances and states. Support keyboard access, visible focus, labels/automation names, non-color feedback, and high-contrast/reduced-motion review. These targets alone do not prove full accessibility conformance.
- Prefer efficient native controls/templates and restrained effects. Avoid excessive nested visual trees, animations, blur/transparency, and repeated expensive shadows. Preserve text readability and control boundaries; measure switching/resizing on agreed Windows hardware and remove decoration before compromising reliability.
