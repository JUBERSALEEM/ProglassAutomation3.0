# 07 — Website integration contracts

The customer website (Vercel + Supabase) and the desktop are two sides of one
pipeline: the website owns **intake** (submissions, documents, reports, chat),
the desktop owns **processing** (register, workflow, BOQ, and later
PI/JO/DN/TI). This document is the contract for the two optional write
directions — both are **additive, opt-in, and website-side-deployed**.

**Ground truth.** The contracts below were verified against the website
source: branch `arena/2611f8ff-proglassautomationadv` of
`JUBERSALEEM/ProGlassAutomationADV`, files `website/supabase-inquiry-intake.sql`
(phase 8A), `supabase-inquiry-intake-phase8c-inbox.sql` (phase 8C),
`supabase-inquiry-estimator-phase9d-communication.sql` (phase 9D),
`supabase-inquiry-estimator-phase9e-handoff.sql` (phase 9E),
`supabase-user-profiles.sql`, `supabase-global-chat*.sql`, and
`website/scripts/inquiry-inbox-bridge.mjs`.

Verified names (do not guess, these are the real ones):

| Thing | Real name |
| --- | --- |
| Submissions table | `public.inquiry_customer_submissions` |
| Submission status values | `submitted / under_review / accepted / rejected / downloaded / closed` (CHECK constraint) |
| Documents table | `public.inquiry_customer_documents` |
| Audit events table | `public.inquiry_customer_events` (event types: `submitted / document_registered / status_changed / download_authorized`) |
| Delivery ledger | `public.inquiry_customer_deliveries` |
| Operator roles | `public.inquiry_operator_roles(user_id, role, enabled)` with roles `inquiry_viewer / inquiry_auditor / inquiry_admin / inquiry_bridge / inquiry_estimator` |
| Role gate helper | `public.has_inquiry_role(text[])` |
| Per-inquiry chat table | `public.inquiry_communications` (phase 9D) |
| Author names | `public.user_profiles(user_id, display_name, …)` |
| Inbox RPCs (already ported) | `plan_customer_inquiry_deliveries_v2`, `plan_customer_inquiry_delivery_documents`, `acknowledge_customer_inquiry_delivery_v2` |

The load-bearing inbox contract (plan / documents / acknowledge / storage
download, manifest v2) is **already implemented** in
`Inquiry/Services/Inquiry/InquiryInbox/` and was checked line-by-line against
the Node bridge: same routing validation, folder layout, canonical manifest,
integrity checks, ack parameters and storage policy (phase 8C grants the
`inquiry_bridge` role the bucket SELECT policy). Nothing in this document
changes it.

Two facts that drive the design:

1. **The `status` column is closed vocabulary** (the CHECK constraint above).
   Desktop pipeline states (`prepared / sent / confirmed / hold / cancelled`)
   therefore go to **new additive `pipeline_*` columns** — the website's own
   status machine and every existing page keep working unchanged.
2. **The chat read RLS does not cover the bridge** (`inquiry_communications`
   is readable by `inquiry_admin / inquiry_auditor / active estimator / the
   customer only`). The desktop pulls chat through a **new bridge-scoped
   read-only RPC** (§2), in the same style as the phase 9E inbox RPCs.

## 1. Pipeline status write-back (desktop → website)

**Purpose:** the website's reports pages read `inquiry_customer_submissions`
directly; with `pipeline_status` they show what the desktop did with a
submission (*prepared / sent / confirmed / hold / cancelled*), not just
"downloaded".

**State: deployed both sides, OFF by default on the desktop.** The website
function was deployed and verified on 2026-10-24 to project
`afpbdyamedpanwijxghk` (ADV branch `arena/2611f8ff-proglassautomationadv`,
commits `5bd3685`/`0c58f29`; Vercel deploy `dpl_5gEaScU9JivZaQDsfS2FmYtPZ9dN`
in production; SQL kept at
`website/supabase-inquiry-inbox-bridge-phase12.sql` there). The enabled
bridge account is `up17mix@gmail.com`
(`0568fecb-0f8e-4f1d-9d77-845a5be0cbbc`) — it must carry the
`inquiry_bridge` role; the disabled `ffyassh@gmail.com` account is refused
by the function. The desktop enables it per machine via the inbox settings
toggle "Report status to website" (`reportStatusToWebsite`, default
`false`). Desktop side: `InquiryStatusReporter` fires **after** a
successful local transition (editor page). Best-effort: remote failure
never blocks, delays or rolls back the local change — the desktop register
is the source of truth. Only inquiries ingested from the website
(non-empty `WebSubmissionId`) are ever reported; manual inquiries are
silent. The website's operator submissions pages now display the state
read-only ("Desktop: Prepared" etc.); customer-facing reads strip the
`pipeline_*` columns, so internal workflow state never reaches a customer
browser.

### 1.1 Contract

- **RPC:** `update_customer_inquiry_status_v1`
- **Caller:** the same inquiry-inbox **bridge service account** the desktop
  already signs in with (no new account, no anon exposure). The account must
  carry the `inquiry_bridge` role in `public.inquiry_operator_roles` — the
  same role gate the phase 9E inbox RPCs use.
- **Parameters:**

| Parameter | Type | Meaning |
| --- | --- | --- |
| `p_submission_id` | `uuid` | The submission row the desktop ingested (`WebSubmissionId`). |
| `p_status` | `text` | One of: `prepared`, `sent`, `confirmed`, `hold`, `cancelled`. (`received` is never sent — the website already knows the submission.) |
| `p_note` | `text` | Free context, e.g. the desktop inquiry number (`INQ-2026-000123`). |

- **Behaviour:** last write wins per submission; idempotent. Unknown
  `p_status` or unknown submission → exception (fail loud, not silent).
  Writes a `status_changed` audit event with `source: 'desktop_inbox'` in
  the details.

### 1.2 Website-side SQL (deploy to the website's Supabase)

Apply after the existing phase 8A/8C/9E migrations. Additive only.

```sql
-- DESKTOP INBOX — PIPELINE STATUS WRITE-BACK (see ProglassAutomation3.0 docs/07)
-- Additive only. Apply after Phase 8A/8C and Phase 9E.
BEGIN;

-- 1) Additive pipeline columns on the submissions table.
ALTER TABLE public.inquiry_customer_submissions
  ADD COLUMN IF NOT EXISTS pipeline_status     text,
  ADD COLUMN IF NOT EXISTS pipeline_note       text,
  ADD COLUMN IF NOT EXISTS pipeline_updated_at timestamptz,
  ADD COLUMN IF NOT EXISTS pipeline_updated_by text;

-- 2) The RPC the desktop calls (phase 9E style: role-gated, definer).
CREATE OR REPLACE FUNCTION public.update_customer_inquiry_status_v1(
  p_submission_id uuid,
  p_status text,
  p_note text
)
RETURNS void
LANGUAGE plpgsql SECURITY DEFINER SET search_path = public, pg_temp AS $$
DECLARE v_old text;
BEGIN
  IF NOT public.has_inquiry_role(ARRAY['inquiry_bridge']) THEN
    RAISE EXCEPTION 'Inquiry bridge role required.' USING ERRCODE = '42501';
  END IF;
  IF p_status NOT IN ('prepared', 'sent', 'confirmed', 'hold', 'cancelled') THEN
    RAISE EXCEPTION 'Unknown pipeline status: %', p_status USING ERRCODE = '22023';
  END IF;
  SELECT pipeline_status INTO v_old
    FROM public.inquiry_customer_submissions
   WHERE id = p_submission_id FOR UPDATE;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'Submission not found.' USING ERRCODE = 'P0002';
  END IF;
  UPDATE public.inquiry_customer_submissions
     SET pipeline_status     = p_status,
         pipeline_note       = coalesce(p_note, ''),
         pipeline_updated_at = now(),
         pipeline_updated_by = auth.uid()::text
   WHERE id = p_submission_id;
  INSERT INTO public.inquiry_customer_events(submission_id, event_type, details, customer_visible)
  VALUES (p_submission_id, 'status_changed',
          jsonb_build_object('source', 'desktop_inbox', 'from', v_old, 'to', p_status, 'note', coalesce(p_note, '')),
          false);
END $$;
REVOKE ALL ON FUNCTION public.update_customer_inquiry_status_v1(uuid, text, text) FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION public.update_customer_inquiry_status_v1(uuid, text, text) TO authenticated;

NOTIFY pgrst, 'reload schema';
COMMIT;
```

Notes for the website deployer:
- `pipeline_*` is plain column data — the reports page reads it with the
  existing `SELECT` grant/policies; **no extra RPC is needed to read it**.
  (Add it to the reports UI as a separate, additive change — the desktop
  does not depend on the website rendering it.)
- The event row is `customer_visible = false` so customers never see the
  desktop's internal pipeline state; admins/auditors see it in the event
  audit.
- No RLS changes: the existing `inquiry_customer_submissions` policies
  (customer / viewer / auditor / admin) already cover reads; the write path
  is definer + role-gated, exactly like `acknowledge_customer_inquiry_delivery_v2`.

### 1.3 Verification (shop PC)

1. Deploy §1.2 to the website Supabase (SQL editor / migration).
2. Desktop → Inbox → enable **Report status to website** → Save.
3. Open a website-ingested inquiry → **Prepare** (or Send/Confirm/Hold/Cancel).
4. Website Supabase: `SELECT submission_reference, status, pipeline_status, pipeline_note, pipeline_updated_at FROM public.inquiry_customer_submissions ORDER BY pipeline_updated_at DESC LIMIT 5;`
   → the row's `pipeline_*` values are set; the `inquiry_customer_events`
   table gained a `status_changed` row with `source: 'desktop_inbox'`.
5. Disable the toggle → transitions stop being mirrored (ack still flows).

## 2. Chat sync (website → desktop) — phase 2

The website's **per-inquiry chat** (`/[locale]/inquiries/chat`, component
`CustomerInquiryChatWorkspace`, backed by `public.inquiry_communications`)
is operator↔customer messaging on one thread per submission. The desktop
already has a natural home for it: **every inquiry carries a Communications
& activity feed** (`InquiryCommunication`) shown on the editor page — today
it records "Received from customer website" at ingest.

**State: deployed both sides, OFF by default on the desktop.** The website
function was deployed and verified on 2026-10-24 (same deployment as §1 —
see the note there; verified there to return the real thread, including
author display names from `user_profiles`). On every inbox check the
service walks the **local ledger** (all ingested inquiries, newest first,
capped at 200) and pulls that submission's chat messages into the local
feed. It walks the ledger — not the inbox plan — because the plan RPC only
lists not-yet-delivered submissions while chat keeps flowing *after*
delivery. Dedupe is on the website message id (new `ExternalId` column on
`InquiryCommunications`, migration 1007), so re-syncs are idempotent.
Enabled per machine via the inbox settings toggle "Sync website chat"
(`syncWebsiteChat`, default `false`). Until the website RPC is deployed the
toggle is inert and the sync status line says so neutrally — files and inbox
are unaffected.

### 2.1 Contract

- **RPC:** `list_customer_inquiry_communications_v1`
- **Caller:** the bridge service account (`inquiry_bridge` role) — read-only.
- **Parameters:** `p_submission_id uuid`.
- **Returns (ordered oldest → newest):**

| Column | Type | Meaning |
| --- | --- | --- |
| `id` | `uuid` | Message id — the desktop dedupe key. |
| `visibility` | `text` | `customer` or `internal`. |
| `message_kind` | `text` | `message` or `missing_information_request`. |
| `request_status` | `text` | `open` / `resolved` for requests, null for messages. |
| `body` | `text` | The message (≤ 4000 chars on the website). |
| `author_display_name` | `text` | From `public.user_profiles` (fallback "Website user"). |
| `created_at` | `timestamptz` | Website timestamp. |

- **Mapping into the desktop feed:**

| Website | Desktop `InquiryCommunication` |
| --- | --- |
| `message_kind = missing_information_request` | `EventType = "Website Information Request"`, title per visibility, description = body + `(open)`/`(resolved)` |
| `message_kind = message`, `visibility = customer` | `EventType = "Website Chat"`, title `Website message from {author}` |
| `message_kind = message`, `visibility = internal` | `EventType = "Website Chat"`, title `Internal website note` |

### 2.2 Website-side SQL (deploy to the website's Supabase)

```sql
-- DESKTOP INBOX — READ-ONLY PER-INQUIRY CHAT PULL (see ProglassAutomation3.0 docs/07)
-- Additive only. Apply after Phase 9D (inquiry_communications) and
-- supabase-user-profiles.sql.
BEGIN;

CREATE OR REPLACE FUNCTION public.list_customer_inquiry_communications_v1(p_submission_id uuid)
RETURNS TABLE (
  id uuid,
  visibility text,
  message_kind text,
  request_status text,
  body text,
  author_display_name text,
  created_at timestamptz
)
LANGUAGE plpgsql STABLE SECURITY DEFINER SET search_path = public, pg_temp AS $$
BEGIN
  IF NOT public.has_inquiry_role(ARRAY['inquiry_bridge']) THEN
    RAISE EXCEPTION 'Inquiry bridge role required.' USING ERRCODE = '42501';
  END IF;
  RETURN QUERY
    SELECT c.id, c.visibility, c.message_kind, c.request_status, c.body,
           coalesce(p.display_name, 'Website user'), c.created_at
      FROM public.inquiry_communications c
      LEFT JOIN public.user_profiles p ON p.user_id = c.author_user_id
     WHERE c.submission_id = p_submission_id
     ORDER BY c.created_at, c.id;
END $$;
REVOKE ALL ON FUNCTION public.list_customer_inquiry_communications_v1(uuid) FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION public.list_customer_inquiry_communications_v1(uuid) TO authenticated;

NOTIFY pgrst, 'reload schema';
COMMIT;
```

Notes for the website deployer:
- Read-only: it adds **no write path** and **no new RLS policy** — the
  existing `inquiry_communications` policies are untouched.
- The bridge sees both visibilities by design: the desktop is the operator
  workspace, and internal notes (admin/estimator) are part of the working
  thread. The desktop never *posts* — see §4 before adding that.
- The `user_profiles` join is cosmetic (display name); a missing profile
  row degrades to "Website user", never an error.

### 2.3 Verification (shop PC)

1. Deploy §2.2 to the website Supabase.
2. Desktop → Inbox → enable **Sync website chat** → Save → Check now.
3. On the website, post a message on the inquiry's chat (`/inquiries/chat`)
   — both a plain customer message and, as staff, an internal note.
4. Desktop → open the ingested inquiry → **Communications & activity**: the
   messages appear with author, text and time. Re-run the sync → **no
   duplicates** (dedupe by message id).
5. Disable the toggle → the feed keeps its history; no further pulls.

## 3. The global community room — deliberately out of scope

The website also has a **community room** (`/[locale]/chat`, table
`global_chat_messages`) — a signed-in members' room with replies, mentions,
receipts and realtime. It is **not per-inquiry data**: no submission id, no
customer context, nothing the desktop workflow consumes. Pulling it into the
desktop would mean a new page, its own dedupe and (for liveliness) a
realtime dependency, for zero workflow value. **Decision: the desktop syncs
only the per-inquiry chat channel.** If that ever changes, it is a new
phase, not a flag.

## 4. Phase 3 — chat two-way (design only, not built)

Only start after phase 2 has proven the message contract in production:

- **New RPC** `post_customer_inquiry_communication_for_bridge(p_submission_id uuid, p_body text)`
  (phase 9D style, `inquiry_bridge` role-gated, definer): inserts a
  `message_kind = 'message'`, **`visibility = 'internal'`** row authored by
  the bridge user, plus the `message_created` audit event.
- Why `internal` only: the website's phase 9D rules promise *customers may
  only send customer-visible messages*; the desktop must never post into the
  customer-visible thread under a machine identity. Internal notes are
  visible to admin/estimator on the website's chat UI and invisible to the
  customer — safe both ways.
- Desktop: a composer on the communications feed + an offline outbox
  (queued posts replayed on the next sync) — the inbox sync cycle is the
  transport; **no realtime** at this phase.
- Supabase Realtime for live push is the *last* thing, and only if the
  owner actually wants the feed to update without a sync tick.

## 6. Security (all phases)

- The **bridge service account** remains the only desktop-side credential;
  the desktop never signs in with an operator's website account.
- Both new RPCs are `SECURITY DEFINER`, role-gated to `inquiry_bridge`,
  `REVOKE ... FROM PUBLIC, anon`, `GRANT ... TO authenticated` — the exact
  pattern of the phase 9E inbox RPCs. Anonymous web traffic cannot call
  them.
- Chat pull is **read-only**; the desktop adds no cross-inquiry browsing
  surface and no customer-visible write path (until §4, and then only
  `internal` visibility).
- Desktop writes are best-effort and opt-in per machine; a failed remote
  call never blocks or rolls back local work.
