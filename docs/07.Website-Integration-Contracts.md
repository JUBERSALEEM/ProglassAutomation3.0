# 07 — Website integration contracts

The customer website (Vercel + Supabase) and the desktop are two sides of one
pipeline: the website owns **intake** (submissions, documents, operator
reports/chat), the desktop owns **processing** (register, workflow, BOQ, and
later PI/JO/DN/TI). This document is the contract for the two optional
write directions — both are **additive, opt-in, and website-side-deployed**.

Nothing in this document changes the load-bearing inbox contract
(plan / document / acknowledge RPCs, manifest v2) — see
`Inquiry/Services/Inquiry/InquiryInbox/InquiryInboxModels.cs`.

---

## 1. Pipeline status write-back (desktop → website)

**Purpose:** the website's reports page (and later chat) shows what the
desktop did with a submission — *prepared / sent / confirmed / hold /
cancelled* — so an operator checking the website sees the inquiry's real
status, not just "downloaded".

**State: app side implemented, OFF by default.** The website function below
must be deployed to the website's Supabase before enabling the toggle.
Until then the desktop behaves exactly as before (download ack only).

### 1.1 Contract

- **RPC:** `update_customer_inquiry_status_v1`
- **Caller:** the same inquiry-inbox **bridge service account** the desktop
  already signs in with (no new account, no anon exposure).
- **Parameters:**

| Parameter | Type | Meaning |
| --- | --- | --- |
| `p_submission_id` | `uuid` | The submission row the desktop ingested (`WebSubmissionId`). |
| `p_status` | `text` | One of: `prepared`, `sent`, `confirmed`, `hold`, `cancelled`. (The website already knows `received` — it is never sent.) |
| `p_note` | `text` | Free context, e.g. the desktop inquiry number (`INQ-2026-000123`). |

- **Behaviour:** last write wins, idempotent per (submission, status, note).
  Unknown `p_status` → raise an exception (fail loud, not silent).
  The function must be `SECURITY DEFINER` and callable by the bridge
  account's role — same trust path as the existing
  `acknowledge_customer_inquiry_delivery_v2`.
- **Desktop side:** `InquiryStatusReporter` fires **after** a successful
  local transition (editor page). Best-effort: remote failure never blocks,
  delays or rolls back the local change — the desktop register is the source
  of truth. Enabled per machine via the inbox settings toggle
  "Report status to website" (`reportStatusToWebsite`, default `false`).

### 1.2 Website-side SQL (deploy to the website's Supabase)

> **Confirm the table name** — below it is `public.customer_inquiry_submissions`,
> the table `plan_customer_inquiry_deliveries_v2` reads from. Adjust if your
> deployment names it differently. The columns are **new and additive** —
> the website's existing status column and CHECK constraints are untouched,
> so the current reports page keeps working unchanged.

```sql
-- 1) Additive pipeline columns on the submissions table.
alter table public.customer_inquiry_submissions
  add column if not exists pipeline_status      text,
  add column if not exists pipeline_note        text,
  add column if not exists pipeline_updated_at  timestamptz,
  add column if not exists pipeline_updated_by  text;

-- 2) The RPC the desktop calls.
create or replace function public.update_customer_inquiry_status_v1(
  p_submission_id uuid,
  p_status text,
  p_note text
)
returns void
language sql
security definer
set search_path = public
as $$
  update public.customer_inquiry_submissions s
     set pipeline_status     = p_status,
         pipeline_note       = coalesce(p_note, ''),
         pipeline_updated_at = now(),
         pipeline_updated_by = auth.uid()::text
   where s.id = p_submission_id
     and p_status in ('prepared', 'sent', 'confirmed', 'hold', 'cancelled');

  if not found then
    raise exception 'Unknown pipeline status: %', p_status;
  end if;
$$;

-- Grant to the bridge account's role (replace the placeholder role name —
-- the same role that may call acknowledge_customer_inquiry_delivery_v2).
-- grant execute on function public.update_customer_inquiry_status_v1(uuid, text, text) to <bridge_role>;
```

Notes for the website deployer:
- `auth.uid()` is null for service-role/bridge calls; if you want the
  operator name stamped, extend the function to accept `p_actor text`.
- RLS: the existing submissions policy set already applies — no changes.
- The reports page can then read `pipeline_status` directly (it is plain
  column data; no extra RPC needed to *read* it).

### 1.3 Verification (shop PC)

1. Deploy §1.2 to the website Supabase.
2. Desktop → Inbox → enable **Report status to website** → Save.
3. Open a website-ingested inquiry → **Prepare** (or Send/Confirm…).
4. On the website: the submission row's `pipeline_status`/`pipeline_updated_at`
   are set; the reports page shows the new status.
5. Disable the toggle → transitions stop being mirrored (ack still flows).

## 2. Chat sync (website → desktop) — plan, not yet built

The website's chat page is operator↔customer messaging. The desktop already
has a natural home for it: **every inquiry carries a Communications &
activity feed** (`InquiryCommunication`: event type, title, description,
actor, occurred-at) shown on the editor page — today it records "Received
from customer website" at ingest.

**Recommendation: three phases, in order.** Do not jump to phase 3.

| Phase | What | Desktop work | Website work |
| --- | --- | --- | --- |
| **P1 — status write-back** | Reports page shows desktop status | **Done (off by default)** | Deploy §1.2 SQL |
| **P2 — chat read** | Inbox pull fetches that inquiry's website chat messages and appends them to the local communications feed (newest first, deduped by message id). No new page — the editor's existing feed is the chat screen. | ~one client call (`list_customer_inquiry_messages` RPC) + ingest into the feed | One read-only RPC returning `{id, direction, sender, body, sent_at}` per submission |
| **P3 — chat two-way** | Desktop replies appear on the website (and ideally near-real-time) | Composer on the feed + `post_customer_inquiry_message` RPC call | Write RPC (+ Supabase Realtime channel if live push is wanted) |

**Why phased:**
- P1 has no dependency on any new website surface beyond a few columns.
- P2 reuses the existing 5-minute inbox sync (no realtime dependency, no new
  page) and reuses the feed UI that already exists — the cheapest "chat
  sync" that is actually useful (the desktop sees what the customer said).
- P3 is the only phase that needs realtime; it should only be built after
  P2 proves the message contract, because realtime + write-back multiplies
  the failure surface (ordering, dedupe, offline queue).

**What is needed before P2 can start:** the message table/RPC contract from
the website deployment (message id format, direction values, how the chat
thread is keyed — by submission id, presumably). Without the website-side
contract, the desktop side would be built against guesses.

**Security note (all phases):** the bridge account stays the only
desktop-side credential; the desktop never logs in with the operator's
website account. Chat messages stay inside the inquiry they belong to —
no cross-inquiry browsing surface is added to the desktop.
