# 12 — Module specifications

Scope and dependency specifications for every module in the approved
[business-module roadmap](11.Business-Module-Roadmap.md). One section per module,
same order, same shape:

**Purpose · Owns · Depends on · Migration · Tests · Excluded · Open questions.**

These are **planning specifications, not authorizations**. A specification says
what a module is allowed to be; implementation still needs the owner's approval
for that module, and every transaction module also waits for gate `G1`.

Where a detail is genuinely undecided it is listed under *Open questions* rather
than filled in. Nothing here invents a requirement the owner has not stated.

---

## `step3` — User Management

**Purpose.** Give the ERP managed user identities, roles and permissions, so that
"who did this" can be answered by a reference instead of a typed name.

**Status.** Implemented 2026-10-27 (source + migration 1013 + portable checks).
Windows build/runtime and nine-theme verification outstanding.

**Owns, as built.** `Users`, `Departments` and `Roles` in the existing
`inquiries.db`. A user carries a stable id, full name, username (the login
identifier), department, role, active flag, created/updated timestamps and the
stable ids of the administrator who granted and last changed access.

**Decisions this stage had to make, and why**

| Question from the earlier spec | Answer as built |
| --- | --- |
| Fixed roles or editable table? | Both catalogues are **tables** (`Departments`, `Roles`) seeded with the agreed values. Codes are stable and renameable wording is data, so a department can be added without a redesign or a rebuild. |
| Does an enforcement point exist? | Yes. The repository resolves the operator from the workstation account **inside the write transaction** and refuses; hiding a button is never the gate. |
| One representative per client, or many? | **Not built in this stage** — see "Deferred" below. |
| Authentication mechanics? | **None, deliberately.** The application has no credentialed login. Identity is the Windows account already read by `CurrentOperator`, matched to a user by username. No password, hash, salt or token column exists anywhere in this stage. |

**Authorization, exactly as enforced.** An identified, active user whose role is
Administrator may add, edit, activate, deactivate and re-role users. An inactive
user may perform no protected operation. The last active Administrator cannot be
deactivated, demoted or re-roled, and the count is read in the same transaction as
the write. A caller whose workstation account matches no user row is refused; there
is no anonymous fallback. **No per-module permission matrix was invented** for
Accountant, Salesman, Estimator, Foreman, Cutting or Double Glazing: those modules
do not exist yet, and a fabricated grid would have to be undone.

**A department is never a permission.** Department answers "which team"; role
answers "what may be done". `step3.a.4` does not read the department at all, and a
source check enforces that.

**First run.** An empty directory is a state, not a refusal. `step3.b.6.FirstRunService`
owns the flow: it inspects the directory, reads the Windows account the process runs
under (never a typed username), calls the repository's guarded
`RegisterFirstAdministratorAsync` — which re-checks emptiness inside its transaction
and re-counts before committing — and then verifies that the new row is matched by
the workstation account. The shell shows `step3.d.3.FirstRunSetupView` as a gate over
the whole shell while setup is required, and selects the Users workspace when it
completes; the Users page presents the same service as a card for a deferred setup.
A failed attempt leaves the form usable for a retry, an inactive match is reported
as inactive and never re-activated, and no password, default account or anonymous
access exists anywhere in the flow.

**Prepared By.** `UserSession.CaptureStampAsync` returns the stable user id plus a
snapshot of the name and role at signing time. Records persist the id and the
snapshot, so a later rename relabels nothing historical. The stage's own
`Users.CreatedByUserId` / `UpdatedByUserId` are the working example in this build.

**Migration.** 1013, appended to the existing chain after 1012. Purely additive:
no table, column, index or row is dropped or rewritten, so Clients and Inquiries
data are untouched. Re-running is a no-op.

**Layout.** All gaps and sizes in the two views come from the shared layout scale
in the theme contract (`UiGapField`, `UiGapGroup`, `UiGapSection`, `UiGapAction`,
`UiGapCluster`, `UiPagePadding`, `UiCardPadding`, `UiActionMinHeight`,
`UiActionPadding`), defined identically in all eighteen theme dictionaries. The
command bar is one row of two wrapping clusters (filters in the flexible column,
actions content-sized, each filter carrying its selection on its face — "All
departments" / "All roles" before a choice, the catalogue's own wording after it —
and its selection re-applied after the catalogue loads), page padding is applied
once per view, every card on the page pins `UiCardPadding` so the bar's contents
and the register's first column share one left edge in all nine themes, the editor
scrolls in one region inside a content-sized card, action buttons are at least
36 px high with 8 px inside a cluster and 16 px between clusters, and the shell
keeps the sidebar and content in separate columns with the content clipped to its
own region. The permanent rules behind those choices are A–J in
`docs/00.Project-Rules.md`.

**Tests.** `step3.f.1` (rules, catalogue, authorization decisions,
last-administrator guard, the first-run gate including two concurrent bootstrap
attempts and an inactive match, migration 1013 against an isolated database with an
existing client row, and the repository round-trip including a non-administrator
being refused by the write path). `step3.f.2` (source/contract checks: shell
wiring, one migration chain, no credential storage, department never authorized,
single catalogue definition, no delete path, attribution by id, theme contract, and
the layout rules — wrapping command rows, one page padding, one scroll region,
action-button height and gap tokens, contract tokens in all nine packages, no
floating shell control).

**Deferred, and why.** The client's representative reference that `step2` reserved
for this stage is **not** added here: the owner scoped this round to User
Management only, and changing the Clients screen was not in it. The dependency is
recorded in `docs/05` with the exact shape it should take when approved (a nullable
`Clients.RepresentativeUserId` in a later migration plus one selector in the client
editor). Authentication, login UI, organisation hierarchy and licensing remain
excluded.

## `step4` — Company Profile

**Purpose.** Record the company's own business identity and the settings future
documents need, kept separate from user identity and from client records.

**Owns.** The company profile record (legal/trading name, address, TRN and other
document-header facts) and the settings that belong to the company rather than to
a user or a client.

**Depends on.** `step3` only in the weak sense that edits should be attributable;
it has no hard dependency on client data.

**Migration.** A single-row company profile table on the existing chain. One row,
enforced — not a directory of companies.

**Tests.** Single-row invariant; required-field validation; TRN/format rules
matching the client rules where they overlap; no second "company" concept appears
later in a document module.

**Excluded.** User identity, client data, branding assets if not approved,
document numbering (which belongs with the first document module), licence data.

**Open questions.** Exactly which fields the documents need; whether a logo or
letterhead asset is stored here; whether VAT/currency defaults live here or in the
document modules.

## `step5` — Project Records & Inquiry Integration

**Purpose.** Establish project records, and connect the existing Inquiry module to
the client directory through a stable client reference.

**Owns.** The project record (a job/site a client's inquiries belong to); a
**new nullable** `ClientId` on inquiries, and a nullable `ProjectId` if projects
are confirmed; the pickers that let an operator choose an existing client/project
while still allowing one-off free-text customers.

**Depends on.** `step2` (clients), `step3` (users), the existing Inquiry module.

**Migration.** A projects table, plus nullable columns added to `Inquiries`. The
existing text columns (`CustomerName`, `CustomerLocation`, `Project`, `Salesman`,
`PreparedByName`, `PreparedByRole`) and the existing integer placeholders
(`CustomerId`, `ProjectId`, `SalesmanId`, `PreparedByUserId`) are **not**
repurposed, renamed or dropped. Historical inquiries keep `ClientId = NULL` and
their text exactly as it is.

**Tests.** Every existing inquiry survives the migration byte-for-byte in its text
columns; a source check that **no code path matches historical inquiries to
clients by name**; FK behaviour on deactivating a client (deactivation is not
deletion); editor round-trip with and without a selected client; project
uniqueness/numbering if projects are approved.

**Excluded.** Automatic backfill or name matching of history; removing the
free-text fallback; project costing, budgets or profitability; moving inquiry
ownership between modules.

**Open questions.** Is a Project record required for this stage, or is the stage
only the client link with projects deferred? Does a project carry a number, a
status, both? Can one inquiry belong to several projects?

## Gate `G1` — Foundation Review

Not a module and not a feature number. A review of `step2`–`step5` together,
producing a checklist and an evidence-based acceptance report; see
[the roadmap §3](11.Business-Module-Roadmap.md) for the six required areas. It
writes no feature code and blocks `step6`–`step11` until the owner accepts it.

## `step6` — Proforma Invoice (PI)

**Purpose.** Turn a confirmed inquiry into a priced proforma invoice carrying the
inquiry's scope of supply, so a quote becomes a document the customer can act on.

**Owns.** PI header and line items, PI numbering, PI status, and the conversion
from an inquiry (including which inquiry rows may be converted and which may not).

**Depends on.** Gate `G1`; `step5` (client/project reference on the inquiry);
`step3` (users for prepared/checked/issued); `step4` (company header facts);
the Inquiry BOQ as the source of scope.

**Migration.** PI tables on the existing chain. Inquiry rows gain a PI reference
only if the approved design says so; the inquiry's own snapshot columns are not
rewritten.

**Tests.** Conversion mapping (BOQ rows → PI lines) including empty, partial and
duplicated scope; totals, tax and rounding with exact expected values; numbering
uniqueness and gap policy; status transitions and their refusals; conversion
blocked twice for the same inquiry; validation of customer/company/TRN.

**Excluded.** Anything not in the approved PI scope — printing/PDF, e-mail
delivery, job-order generation, price-list engines — are separate decisions, not
side effects of building the PI.

**Open questions.** Numbering scheme; VAT and currency rules; whether pricing is
computed per line or per scope item; how much of the ADV nine-step pricing wizard
(if any) is in scope for V3.

## `step7` — Job Order (JO)

**Purpose.** Turn an accepted proforma into a production instruction for the shop
floor.

**Owns.** JO header/lines, JO numbering, JO status, and the production view of the
work (as distinct from the priced view the PI already holds).

**Depends on.** `step6` (a JO comes from an accepted PI); `G1`.

**Migration.** JO tables on the existing chain; a PI→JO reference.

**Tests.** PI→JO mapping; the JO's own sheet/cutting data is stored separately
from the PI's; status transitions; numbering; refusal to create a second JO from
one PI without an approved rule.

**Excluded.** Stock/optimisation engines, machine output formats, shop-floor
scheduling.

**Open questions.** Does the JO carry its own cutting sheet in this stage; what
must exist on it before it is printable; is JO allowed before the PI is fully
paid — a commercial rule the owner must state.

---

## `step8` — Delivery Note (DN)

**Purpose.** Record what physically left the premises against a job order.

**Owns.** DN header/lines, DN numbering, DN status, and the quantity delivered
against the ordered quantity.

**Depends on.** `step7`; `G1`.

**Migration.** DN tables on the existing chain; a JO→DN reference, with
partial-delivery support if approved.

**Tests.** Partial and complete deliveries; over-delivery refused; numbering;
status transitions; the ordered-vs-delivered balance cannot go negative.

**Excluded.** Transport/logistics tracking, driver assignment, proof-of-delivery
capture beyond a recorded acknowledgement.

**Open questions.** Are partial deliveries allowed at all; does a DN need
signature/attachment capture; does a DN consume stock in this stage.

---

## `step9` — Tax Invoice (TI)

**Purpose.** Issue the VAT document that bills the delivered work.

**Owns.** TI header/lines, TI numbering, TI status, and the VAT presentation.

**Depends on.** `step8` (delivery) and `step6` (priced values); `G1`.

**Migration.** TI tables on the existing chain, referencing client, company, PI
and DN.

**Tests.** VAT computation with exact expected totals and rounding; totals equal
what was delivered; numbering and cancellation policy; a TI cannot exceed what was
delivered.

**Excluded.** E-invoicing/UBL/QR compliance work is a separate decision, not an
assumption; credit notes are a separate scope.

**Open questions.** Is the TI generated from DN quantities or PI values; what is
the VAT rate policy; are credit notes part of this module or `step10`.

---

## `step10` — Statement

**Purpose.** Present a client's account: what was invoiced, what was received,
what remains.

**Owns.** The statement view over invoices and payments, its date range and its
presentation.

**Depends on.** `step9` (invoices) and a payments/collections source, which does
not exist yet — its own decision.

**Migration.** Payment/receipt storage, if payments are in scope, on the existing
chain.

**Tests.** Opening/closing balance arithmetic with exact expected values; date
range boundaries; a client with no documents; currency consistency.

**Excluded.** Banking integration, reconciliation automation, aged-debt chasing.

**Open questions.** Are payments recorded in this application at all; is the
statement per client or per project; which ageing bands the owner wants.

---

## `step11` — Reports and other required modules

**Purpose.** Placeholder for the reporting layer and anything the owner adds after
the ten modules above exist.

**Owns.** Nothing yet, by design.

**Depends on.** Whatever it reports on.

**Migration.** None until scope exists.

**Tests.** None until scope exists.

**Excluded.** Everything, until its own allocation review.

**Open questions.** All of it — name, scope, whether it splits into several
numbers (`step11`, `step12`, …), and whether a report is a page, an export, or
both. This section is deliberately empty of content rather than filled with
guesses.
