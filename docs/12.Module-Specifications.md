# 12 — Module specifications

Scope and dependency specifications for every module in the approved
[business-module roadmap](11.Business-Module-Roadmap.md). One section per module,
same order, same shape:

**Purpose · Owns · Depends on · Migration · Tests · Excluded · Open questions.**

These are **planning specifications, not authorizations**. A specification says
what a module is allowed to be; implementation still needs the owner's approval
for that module, and every transaction module also waits for gate `G1`.

Where a detail is genuinely undecided it is listed under *Open questions* rather
than filled in. Nothing here invents a requirement the owner has not stated.

## `step3` — User Management

**Purpose.** Give the ERP managed user identities, roles and permissions, so that
"who did this" can be answered by a reference instead of a typed name.

**Status.** Implemented 2026-10-27 (source + migration 1013 + portable checks).
Windows build/runtime and nine-theme verification outstanding.

**Owns, as built.** `Users`, `Departments` and `Roles` in the existing
`inquiries.db`. A user carries a stable id, full name, username (the login
identifier), department, role, active flag, created/updated timestamps and the
stable ids of the administrator who granted and last changed access.

**Decisions this stage had to make, and why**

| Question from the earlier spec | Answer as built |
| --- | --- |
| Fixed roles or editable table? | Both catalogues are **tables** (`Departments`, `Roles`) seeded with the agreed values. Codes are stable and renameable wording is data, so a department can be added without a redesign or a rebuild. |
| Does an enforcement point exist? | Yes, on two layers. The **write** path resolves the signed-in user (a password-verified session, `AuthenticationContext`) and refuses unless that person is an active Administrator. The **read** path applies a ceiling in the query: a non-administrator reads their own user row, the clients they represent and the inquiries they are salesman or preparer of. Hiding a button is never the gate. |
| One representative per client, or many? | **One, and optional.** `Clients.RepresentativeUserId` is a nullable reference into the Users directory (migration 1014), chosen from the active users — salesmen listed first. It is set on create **and on edit**, so an assignment can be changed or cleared; a reference whose user has since been deactivated keeps its own labelled row so a save cannot silently drop it. Unassigned stays valid, so every pre-1014 client row is complete as it stands. |
| Authentication mechanics? | **A password per user, owned by this stage** (round 24, reversing the earlier "no credential" decision). `step3.a.5.UserPassword` stores PBKDF2-HMAC-SHA256 at 210 000 iterations with a per-row 16-byte salt and a 32-byte hash and compares with `CryptographicOperations.FixedTimeEquals`; migration 1015 adds the columns. `step3.d.4.SignInView` covers the shell before any page is reachable. The Windows account survives only as the identity the first-run bootstrap registers. A directory that predates 1015 has users but no password anywhere: sign-in refuses every account, so `step3.b.4.SetFirstPasswordAsync` gives the workstation's **own** active Administrator row its first password, once, and closes the moment any account has one. The same card serves both first-run states. |

**Authorization, exactly as enforced.** An identified, active user whose role is
Administrator may add, edit, activate, deactivate and re-role users. An inactive
user may perform no protected operation. The last active Administrator cannot be
deactivated, demoted or re-roled, and the count is read in the same transaction as
the write. A caller whose workstation account matches no user row is refused; there
is no anonymous fallback. **No per-module permission matrix was invented** for
Accountant, Salesman, Estimator, Foreman, Cutting or Double Glazing: those modules
do not exist yet, and a fabricated grid would have to be undone.

**A department is never a permission.** Department answers "which team"; role
answers "what may be done". `step3.a.4` does not read the department at all, and a
source check enforces that.

**First run.** An empty directory is a state, not a refusal. `step3.b.6.FirstRunService`
owns the flow: it inspects the directory, reads the Windows account the process runs
under (never a typed username), calls the repository's guarded
`RegisterFirstAdministratorAsync` — which re-checks emptiness inside its transaction
and re-counts before committing — and then verifies that the new row is matched by
the workstation account. The shell shows `step3.d.3.FirstRunSetupView` as a gate over
the whole shell while setup is required, and selects the Users workspace when it
completes; the Users page presents the same service as a card for a deferred setup.
A failed attempt leaves the form usable for a retry, an inactive match is reported as
inactive at the sign-in gate and never re-activated, and no default account or
anonymous access exists anywhere in the flow. The first administrator chooses their
own password on that form, so the row it creates is one they can sign in as.

**Prepared By.** `UserSession.CaptureStampAsync` returns the stable user id plus a
snapshot of the name and role at signing time. Records persist the id and the
snapshot, so a later rename relabels nothing historical. The stage's own
`Users.CreatedByUserId` / `UpdatedByUserId` are the working example in this build.

**Session.** `AuthenticationContext` holds the signed-in row and is the only identity
the repository reads: set by a verified sign-in, cleared on sign-out. An
administrator-set password is marked `MustChangePassword` and is replaced on the
sign-in card before the session is handed over; a self-change requires the current
password. Five failed attempts lock the account for 60 seconds, on the row.

**Migration.** 1013, appended to the existing chain after 1012, plus 1014 for the
client's representative reference. Purely additive:
no table, column, index or row is dropped or rewritten, so Clients and Inquiries
data are untouched. Re-running is a no-op.

**Layout.** All gaps and sizes in the two views come from the shared layout scale
in the theme contract (`UiGapField`, `UiGapGroup`, `UiGapSection`, `UiGapAction`,
`UiGapCluster`, `UiPagePadding`, `UiCardPadding`, `UiActionMinHeight`,
`UiActionPadding`), defined identically in all eighteen theme dictionaries. The
command bar is one row of two wrapping clusters (filters in the flexible column,
actions content-sized, each filter showing its selection on its face — "All departments" /
"All roles" before a choice, the catalogue's own wording after one — with its
selection bound as a ROW (a code-string `SelectedValue` applied before the list
exists leaves the box blank) and re-applied after the catalogue loads), page padding is applied
once per view, every card on the page pins `UiCardPadding` so the bar's contents
and the register's first column share one left edge in all nine themes, the editor
scrolls in one region inside a content-sized card, action buttons are at least
36 px high with 8 px inside a cluster and 16 px between clusters, and the shell
keeps the sidebar and content in separate columns with the content clipped to its
own region. The permanent rules behind those choices are A–J in
`docs/00.Project-Rules.md`.

**Control spacing (round 30b).** One token did two jobs: `MarginInline` is a text
token (8 px right, 4 px bottom) and it was spacing every button row in the
application — 24 clickable surfaces inside horizontal rows used it, and 14 more
had no margin at all, so filled pills 36–40 px tall sat 8 px apart or touched.
Two tokens replace it, one per anchoring: `UiGapControl` (16 px **right**, for a
left-anchored row) and `UiGapControlEnd` (16 px **left**, for a right-anchored row,
so the last control stays flush with the card edge). No button, radio button,
check box or chip may be spaced with `MarginInline` again. `step1.d.18` enforces
it — token parity and a 12 px floor in all eighteen theme dictionaries, the ban
on the text token, and the row rule (every surface in a horizontal
`StackPanel`/`WrapPanel` carries the token its anchor calls for). The Theme Studio
and Inquiry screens predate the rule and are frozen at their current counts.

**File structure (round 30b).** Owner rule K: no god files. C# ≤ 400 lines, XAML
≤ 750, styles in their own merged `ResourceDictionary`, one part per job.
`step1.d.19` carries the caps and the frozen list of nineteen pre-existing files
that may be split but never grown. The Company page is the first one split:
`step4.d.1` went from 946 to 724 lines with its styles now in `step4.d.3`.

**Reaching a session (round 30).** The gate is the way in and it can no longer be
lost. `MainWindow.BeginSignInAsync` shows `step3.d.4.SignInView` *before* the step
that can fail, and no `catch` block hides it; a failure goes to
`SignInViewModel.ReportProblem`, i.e. the card's own error box above the retry. When
the first-run check itself cannot be answered, the sign-in gate is opened with that
reason on it instead of both gates being collapsed. The shell additionally draws
`step3.c.5.ShellSessionViewModel` in its banner on every page: who is operating
(name, role and meaning in the tooltip and accessible name) and one action,
**Sign in** when nobody is signed in and **Sign out** when somebody is, plus a
"Sign-in problem" marker carrying the reason. The banner reads
`AuthenticationContext` and writes nothing; the gate and the session remain the only
things that decide who may act.

**Staying signed in on this device (round 32).** Owner instruction: *"remember
the last login until Sign out"*. `step3.b.8.DeviceSessionStore` writes
`%LOCALAPPDATA%\ProGlassAutomation\device-session.json` holding the directory id,
the username, the Windows account the sign-in was made under, the row's password
stamp and a timestamp — never a password, a hash, a salt or a token.
`step3.b.9.RememberedSignIn` resumes it at launch only while every check holds:
the record belongs to this Windows account, the row still exists, is active, has a
password, is not waiting on a password change, and its password stamp has not
moved (an administrator's reset therefore ends the remembered session on this
workstation). Any failed check clears the record and opens the gate with the
reason on it. `AuthenticationContext` raises `SignedIn` as well as `SignedOut`;
the shell remembers on every sign-in and clears the record first thing on
**Sign out**, which is the one explicit "do not remember me". The gate is
unchanged in authority: a resumed session is a session that was already granted
here, and the write paths still resolve the actor from the context.

**Tests.** `step3.f.1` (rules, catalogue, authorization decisions,
last-administrator guard, the first-run gate including two concurrent bootstrap
attempts and an inactive match, migration 1013 against an isolated database with an
existing client row, and the repository round-trip including a non-administrator
being refused by the write path). `step3.f.2` (source/contract checks: shell
wiring, one migration chain, no credential storage, department never authorized,
single catalogue definition, no delete path, attribution by id, theme contract, and
the layout rules — wrapping command rows, one page padding, one scroll region,
action-button height and gap tokens, contract tokens in all nine packages, no
floating shell control).

**The client's representative reference (migration 1014).** `step2` reserved this
for the user stage, and it is now built in the shape that was recorded: a nullable
`Clients.RepresentativeUserId` reference into `Users`, added by migration 1014
after 1013 so the table it points at always exists, plus one picker in the client
editor and one column in the client register. Rules:

* the value is a **user id**, never a typed name — a rename relabels the register
  through the lookup and rewrites no client row;
* the picker offers the **active** users whose role is `SALESMAN`, read from the
  shared catalogue constant rather than a retyped code;
* **unassigned is valid**: null is the state of every client that existed before
  1014, and a client whose salesman has left keeps its stored reference even though
  that person is no longer offered;
* a reference that names no user row is **refused on write** and asserted by the
  migration, so an orphan cannot be created or survive an upgrade.

Authentication, login UI, organisation hierarchy and licensing remain excluded.

## `step4` — Company Profile

**Purpose.** Record the company's own business identity and the settings future
documents need, kept separate from user identity and from client records.

**Status.** Implemented 2026-10-28 (source, migration **1016**, logo asset store,
portable checks). Windows build, runtime and nine-theme rendered verification
outstanding: this environment has no .NET SDK and no WPF runtime, so no build, no
test execution and no screenshot is claimed.

**Repositories inspected.** Both were read before any code was written, and the
SHAs are recorded so the claims below can be re-checked.

| Repository | Branch | Commit inspected |
| --- | --- | --- |
| `JUBERSALEEM/ProGlassAutomation3.0` (this build) | `arena/81baffde-proglassautomation3-0` | checkout at `cd782aa5d752860e1c12e96fe2250a2f8520c1b9` with the previous stages present in the working tree; the branch's pushed tip at inspection was `daaee9354e0c3abc31fa821f4147bd456a63bf90` |
| `JUBERSALEEM/ProGlassAutomationADV` (reference) | `arena/69646c66-proglassautomationadv` | `3cc0cc87f62ed1910e3cfbf4c8317b72b345a94e` (`wpf-2.0.14` also exists in that repository's branch list) |

ADV's `Models/MasterData/SavedCompany.cs`,
`Views/CompanyCenter/CompanyCenterView.xaml` and
`Views/ProformaInvoice/Step1CompanySetup/CompanySetupView.xaml` were read for
BEHAVIOUR only. Two of its choices were deliberately not carried over — see

**Owns, as built.** One `CompanyProfile` row in the existing `inquiries.db`, and
one logo asset inside the application data folder:

| Area | Fields |
| --- | --- |
| Business identity | registered name (required), TRN, address, telephone, website |
| Representative and contact | representative name, representative mobile, company e-mail |
| Banking | bank name, account number / IBAN (two fields, never one blob) |
| Logo | asset file name, placement (`None` / `LeftPortrait` / `TopPanel`), long-edge size in mm |
| Audit | created/updated timestamps and the stable ids of the administrator who first and last saved |

**The logo card (round 32).** The owner's report — *"choose image for logo does
not work"* — was a lifecycle defect, not a dialog defect. `CompanyProfileView`
attached its `RequestLogoPick` handler in the constructor and removed it on
`Unloaded`; the page lives in a `TabControl`, whose template hosts one content
presenter, so leaving the Company tab unloads the view and returning loads it
again. After the first visit to another tab the handler was gone for the rest of
the session. It now attaches on **every** `Loaded` (guarded against a double
attach) and detaches on `Unloaded`. `CanEdit` also reads the process-wide session,
so the view model follows `AuthenticationContext.SignedIn`/`SignedOut` and the view
re-reads the permission on every load; a disabled "Choose image" carries the
reason in its tooltip (`ToolTipService.ShowOnDisabled`), because a dead button
with no message was the complaint.

**The document page (round 32).** Owner instruction: the card must be extended so
the page preview is *"like a read documented page … like it was in mockup"*. The
104 px strip is gone. The card shows a 236 × 300 px sheet on the mockup's grey
stage — `CompanyPageStage` + `CompanyPage` in `step4.d.3` — printing the real
logo, name, address lines, TRN and the contact line from the working copy (so it
changes as you type), with the document body suggested in hairlines beneath the
header. The three placements (left portrait, top masthead, text only) are
unchanged and still one radio group.

**File structure after round 32 (rule K).** `step4.c.1` 999 → 711 lines, with the
logo and preview surface in `step4.c.3` (one `partial` class — same object, same
contract). `step4.d.1` 782 → 468 lines, with the logo card as
`step4.d.4.CompanyLogoPanel` (a `UserControl` that inherits the page's data
context, its styles still merged from `step4.d.3`). The page checks treat the page
and its band files as one page, so a split cannot quietly drop a control.

**Depends on.** `step3` for attribution: the write reads
`AuthenticationContext.Current` and requires an active Administrator. Nothing else
depends on it in the other direction — no inquiry, client or user row is read or
rewritten by this module.

**The single-profile invariant is a constraint, not a convention.**
`CompanyProfile.Id` is a fixed primary key (`SingleId = 1`) with a table `CHECK
("Id" = 1)` and a second `CHECK` on the layout value, and EF maps the key as
`ValueGeneratedNever`. A second profile cannot be inserted by this code, by a
future module, or by hand in SQLite: the database refuses it. The migration also
asserts after the fact that at most one row exists and that every row uses the
fixed id. Hiding a "New" button would have enforced nothing. There is no
`IsDefault`, no `UsageCount` and no company directory — that shape belongs to ADV's
multi-company installer and is explicitly out of scope here.

**Migration.** **1016**, appended to the existing chain after 1015, because that is
the next free version (`AppSchemaMigrations.Inquiries`). Purely additive: one
`CREATE TABLE IF NOT EXISTS` and no seed row, so "never saved" stays
distinguishable from "saved empty", and no Inquiry, Client or User row, column or
index is touched. Re-running is a no-op. The migration is registered on the one
chain, after the initializer has brought `inquiries.db` to the current schema —
there is no second database, no second runner and no `EnsureCreated` owner.

**The logo, and why it is stored the way it is.**

* A picked image is **copied** into `%APPDATA%\ProGlassAutomation\CompanyProfile\`
  under a generated name (`logo-<guid>.<ext>`) and the row stores **that name**.
  ADV stored the picker's absolute path, which breaks the moment the data folder is
  moved or restored on another machine; a name inside the app data folder travels
  with a backup.
* Only PNG, JPG and JPEG are accepted, under 12 MB, and only a bare file name is
  ever resolved — a stored value containing a separator, `..`, an absolute path or a
  foreign extension resolves to `null` instead of reaching the filesystem.
* The copy lands at a temporary name and is then moved into place, so a crash
  mid-copy leaves no asset a row could be pointing at.
* The replaced asset is deleted **only after the transaction commits**. A failed
  save therefore leaves both the stored profile and its logo exactly as they were.
* The preview decodes at a bounded width (`DecodePixelWidth = 640`) rather than at
  full size, and a missing or unreadable file reports itself on the page instead of
  throwing.
* **Aspect ratio is never distorted.** The row stores ONE dimension — the long edge
  in millimetres (8–80) — and the other follows the image's own proportions. ADV
  stored width and height independently, which is exactly how a logo gets stretched.
  Every `<Image>` in the view uses `Stretch="Uniform"`.

**Two placements, both real compositions.** `LeftPortrait` puts a stacked or square
mark to the left of the company name and contact details; `TopPanel` gives a wide
wordmark a full-width masthead with the identity on the right and a rule beneath.
The page previews the chosen composition with the **same** identity, so the choice
is visible rather than two words in a list. A placement with no logo is refused
(the panel would print empty); a stored logo with the `None` placement is allowed,
because "keep the artwork on file, print text only" is a real letterhead choice.

**Validation, as enforced in one place.** `step4.a.2.CompanyProfileRules` is called
by the editor before the write AND by the repository before it persists, so a caller
cannot skip it:

| Rule | Behaviour |
| --- | --- |
| Company name | required after trimming; ≤ 200 characters |
| TRN | optional; exactly 15 digits when present, separators tolerated and stripped |
| Address | optional; ≤ 300 characters; lines preserved, blank lines dropped outright (a gap is not kept as a paragraph break — the letterhead prints the lines and nothing else) |
| Telephone / website / e-mail | optional; shape checked, no invented requirement |
| Representative name / mobile | optional; ≤ 120 / ≤ 30 characters |
| Bank name / account number | optional; account number accepts letters, digits and spaces (IBAN) |
| Logo placement | must be a defined layout, and must have a logo behind it |
| Logo size | clamped to 8–80 mm rather than rejected |
| Every other field | may be empty — a name-only profile saves |

**Layout (owner-approved 2026-10-28, mockup 10 — compact ERP page).** The page
is three bands, not a stack of loose cards:

| Band | Contents |
| --- | --- |
| Header | "Company" + one-line subtitle on the left; on the right the live state chip (**Saved 09:02** / **Unsaved changes** / **Not set up yet**) beside the primary **Save company**, so Save is reachable without scrolling |
| Body | One scroll region. Left: the form card, fields in a 3-per-row star grid (2-per-row where the value is long). Right: a fixed 300 px card holding the letterhead preview, the three placement tiles, the printed-size picker and the logo file chip |
| Footer | Sticky plate: who may edit (in words) on the left, **Revert** and **Save company** on the right, aligned to the same page inset as the cards — the page never ends in dead space |

Spacing is ONE system, the mockup's 8 px grid, and every value is a shared token:
inside a control 8 (`MarginItem`), between fields 12 (`MarginSection`), between
sections 16 (`UiGapGroup`), between the two cards 16 (`UiGapCluster`), page inset 24
(`PaddingPage`). Horizontal and vertical gutters therefore agree, which was the
defect in the first version: a 16 px column gutter against a 24 px page inset made
the cards read as too close and too far apart at the same time, and a
content-height right card left a dead band down the middle.

The three placements are **one radio group rendered as three equal tiles** (still
`RadioButton`, so the group, keyboard behaviour and accessible name are the
platform's), each tile carrying a themed mini diagram — the segmented control from
the approved mockup, not three loose radio buttons with uneven gaps. The logo is a
**file chip**: thumbnail, the file's own name, its pixel size and Remove, with
Choose image beneath it. Section separation is a caption plus a 1 px hairline rule
rather than a new card, which is what keeps the dense page readable at 1280×800.

**Editor states.** Never saved (an empty form that says what saving will do), saved
(the last-saved time and the administrator's name), refused (per-field messages
beside the fields and a sentence above them, with nothing reported as saved), and
read-only (a non-administrator reads the profile, the reason is printed, and the
repository refuses the write as well). Unsaved changes are stated in words. Typing
clears that field's message. Returning to the tab reloads only when the page holds
no unsaved edits, so an edit is never silently discarded.

**Read path for future documents.** `ICompanyProfileReader.GetIdentityAsync()`
returns an immutable `CompanyIdentitySnapshot` — name, TRN, address, telephone,
website, representative, mobile, e-mail, bank name, account number, logo name,
placement and size. Document modules will read that instead of copying company
fields into their own tables. Historical "as it stood when issued" copies are the
document's own business and are NOT implemented here.

**Tests.** `step4.f.1` (rules; logo store; migration 1016 against an isolated
database including the database's own refusal of a second row; the repository
round-trip with anonymous and non-administrator refusals, update-in-the-same-row, a
name-only profile, a refused save leaving the stored profile intact; the logo
lifecycle import → replace → clear, with the old asset checked on disk; and the
editor's dirty/refused/saved/missing-logo/read-only states). `step4.f.2`
(source/contract checks: files and numbering, project inclusion, shell hosting and
the workspace index guard, one migration chain and its additive shape, the
single-profile constraint, name-not-path logo storage with delete-after-commit,
authorisation in the write path with a tracked write, the read path, scope
exclusions, the theme and layout contract of the view, and the documentation
record). Both are Windows-only to RUN and were NOT executed here.

**Excluded.** Multi-company or a company directory; tenant/web tenancy; Supabase;
client or user redesign; new authentication; new themes or private theme
dictionaries; PI/JO/DN/TI or any document rendering; document numbering; licensing;
VAT or currency defaults (unapproved); unrelated refactors.

**Open questions.** Which of these fields each document actually prints (answerable
only when step6+ is approved); whether a future stage needs the identity as it stood
at issue time (a per-document snapshot, not a change to this table); whether the
printed bank details should be split into bank name / account name / IBAN rather
than bank name / account number.

## `step5` — Project Records & Inquiry Integration

**Purpose.** Establish project records, and connect the existing Inquiry module to
the client directory through a stable client reference.

**Owns.** The project record (a job/site a client's inquiries belong to); a
**new nullable** `ClientId` on inquiries, and a nullable `ProjectId` if projects
are confirmed; the pickers that let an operator choose an existing client/project
while still allowing one-off free-text customers.

**Depends on.** `step2` (clients), `step3` (users), the existing Inquiry module.

**Migration.** A projects table, plus nullable columns added to `Inquiries`. The
existing text columns (`CustomerName`, `CustomerLocation`, `Project`, `Salesman`,
`PreparedByName`, `PreparedByRole`) and the existing integer placeholders
(`CustomerId`, `ProjectId`, `SalesmanId`, `PreparedByUserId`) are **not**
repurposed, renamed or dropped. Historical inquiries keep `ClientId = NULL` and
their text exactly as it is.

**Tests.** Every existing inquiry survives the migration byte-for-byte in its text
columns; a source check that **no code path matches historical inquiries to
clients by name**; FK behaviour on deactivating a client (deactivation is not
deletion); editor round-trip with and without a selected client; project
uniqueness/numbering if projects are approved.

**Excluded.** Automatic backfill or name matching of history; removing the
free-text fallback; project costing, budgets or profitability; moving inquiry
ownership between modules.

**Open questions.** Is a Project record required for this stage, or is the stage
only the client link with projects deferred? Does a project carry a number, a
status, both? Can one inquiry belong to several projects?

## `step6` — Proforma Invoice (PI)

**Purpose.** Turn a confirmed inquiry into a priced proforma invoice carrying the
inquiry's scope of supply, so a quote becomes a document the customer can act on.

**Owns.** PI header and line items, PI numbering, PI status, and the conversion
from an inquiry (including which inquiry rows may be converted and which may not).

**Depends on.** Gate `G1`; `step5` (client/project reference on the inquiry);
`step3` (users for prepared/checked/issued); `step4` (company header facts);
the Inquiry BOQ as the source of scope.

**Migration.** PI tables on the existing chain. Inquiry rows gain a PI reference
only if the approved design says so; the inquiry's own snapshot columns are not
rewritten.

**Tests.** Conversion mapping (BOQ rows → PI lines) including empty, partial and
duplicated scope; totals, tax and rounding with exact expected values; numbering
uniqueness and gap policy; status transitions and their refusals; conversion
blocked twice for the same inquiry; validation of customer/company/TRN.

**Excluded.** Anything not in the approved PI scope — printing/PDF, e-mail
delivery, job-order generation, price-list engines — are separate decisions, not
side effects of building the PI.

**Open questions.** Numbering scheme; VAT and currency rules; whether pricing is
computed per line or per scope item; how much of the ADV nine-step pricing wizard
(if any) is in scope for V3.

## `step7` — Job Order (JO)

**Purpose.** Turn an accepted proforma into a production instruction for the shop
floor.

**Owns.** JO header/lines, JO numbering, JO status, and the production view of the
work (as distinct from the priced view the PI already holds).

**Depends on.** `step6` (a JO comes from an accepted PI); `G1`.

**Migration.** JO tables on the existing chain; a PI→JO reference.

**Tests.** PI→JO mapping; the JO's own sheet/cutting data is stored separately
from the PI's; status transitions; numbering; refusal to create a second JO from
one PI without an approved rule.

**Excluded.** Stock/optimisation engines, machine output formats, shop-floor
scheduling.

**Open questions.** Does the JO carry its own cutting sheet in this stage; what
must exist on it before it is printable; is JO allowed before the PI is fully
paid — a commercial rule the owner must state.

## `step8` — Delivery Note (DN)

**Purpose.** Record what physically left the premises against a job order.

**Owns.** DN header/lines, DN numbering, DN status, and the quantity delivered
against the ordered quantity.

**Depends on.** `step7`; `G1`.

**Migration.** DN tables on the existing chain; a JO→DN reference, with
partial-delivery support if approved.

**Tests.** Partial and complete deliveries; over-delivery refused; numbering;
status transitions; the ordered-vs-delivered balance cannot go negative.

**Excluded.** Transport/logistics tracking, driver assignment, proof-of-delivery
capture beyond a recorded acknowledgement.

**Open questions.** Are partial deliveries allowed at all; does a DN need
signature/attachment capture; does a DN consume stock in this stage.

## `step9` — Tax Invoice (TI)

**Purpose.** Issue the VAT document that bills the delivered work.

**Owns.** TI header/lines, TI numbering, TI status, and the VAT presentation.

**Depends on.** `step8` (delivery) and `step6` (priced values); `G1`.

**Migration.** TI tables on the existing chain, referencing client, company, PI
and DN.

**Tests.** VAT computation with exact expected totals and rounding; totals equal
what was delivered; numbering and cancellation policy; a TI cannot exceed what was
delivered.

**Excluded.** E-invoicing/UBL/QR compliance work is a separate decision, not an
assumption; credit notes are a separate scope.

**Open questions.** Is the TI generated from DN quantities or PI values; what is
the VAT rate policy; are credit notes part of this module or `step10`.

---

## `step10` — Statement

**Purpose.** Present a client's account: what was invoiced, what was received,
what remains.

**Owns.** The statement view over invoices and payments, its date range and its
presentation.

**Depends on.** `step9` (invoices) and a payments/collections source, which does
not exist yet — its own decision.

**Migration.** Payment/receipt storage, if payments are in scope, on the existing
chain.

**Tests.** Opening/closing balance arithmetic with exact expected values; date
range boundaries; a client with no documents; currency consistency.

**Excluded.** Banking integration, reconciliation automation, aged-debt chasing.

**Open questions.** Are payments recorded in this application at all; is the
statement per client or per project; which ageing bands the owner wants.
