# 03 — Development and testing workflow

[AGENTS.md](../AGENTS.md) owns permanent agent behavior and the **strict WPF compatibility checklist**. It is incorporated here by reference, not replaced with a second competing checklist. [Project Rules](00.Project-Rules.md) owns filenames; [UI/UX](02.UI-UX-Design-System.md) owns design policy; the [roadmap](04.Project-Roadmap.md) owns acceptance gates.

## Required sequence

1. **Inspect:** read instructions, Git branch/status, existing files, affected callers/resources/configuration, registry, decisions, and scope approval. Preserve unrelated user work. Establish baseline errors before attributing failures to changes.
2. **Plan:** describe the smallest complete approved change in plain language. Verify feature allocation and target framework. Ask about unresolved scope/compatibility decisions rather than inventing answers.
3. **Implement only after approval:** make focused native WPF changes and appropriate small tests. Verify relevant APIs before writing XAML. Apply every strict WPF rule in AGENTS.md: native syntax only; valid content models, properties, resources, namescopes, bindings, commands/events, styles/templates, and class/project references. Enforce the only-standard-WPF-APIs rule from the UI/UX design system doc (no invented properties/enum values; resource keys must resolve; string literals exact; API-surface + string-integrity checks before commit). Do not exchange compatibility for visual effects.
4. **Build:** inspect the actual approved project/solution and SDK first; run its real build on a capable environment and record command, framework, exit result, and errors. Fix introduced errors and distinguish pre-existing failures. Editor plausibility is not compilation evidence.
5. **Test:** run applicable automated checks for nontrivial logic and regressions. For Theme Studio, cover token completeness/appearance selection and relevant view-model commands when introduced. Select a compatible test framework only after approval; do not add testing dependencies speculatively.
6. **Inspect UI:** run the actual WPF application on Windows when possible. Verify light/dark switching, all sample states, keyboard navigation/focus, labels, contrast, resizing/DPI, and performance. Record actual environment and screenshots only from rendered UI, if captured. Browser previews and fabricated screenshots do not verify WPF.
7. **Review:** inspect the diff plus affected references for unrelated changes, unsupported cross-framework syntax, naming inconsistencies, dependency growth, data-loss risks, secrets, and missing tests. Check documentation links and registry/roadmap accuracy.
8. **Report and stop:** follow the completion report in AGENTS.md. Explicitly mark unrun build/tests/visual checks and why. Seek approval at the next phase boundary; never claim execution success without evidence.

## Dynamic-theme verification — required for Phase 01

Use the authoritative [resource contract](02.UI-UX-Design-System.md), not a separate test-only palette. Record concrete commands, environment, results and remaining coverage:

1. Validate both Bento appearance sets against required key names and WPF types; reject missing/incorrect mandatory resources. Add focused negative tests and verify safe application/failure behavior.
2. Test centralized selection state/notifications and resource replacement. In the actual WPF runtime, switch repeatedly while existing controls and a representative dialog are open. Verify the active theme’s reusable styles/templates, popups/lookup scopes and displayed token values; a newly opened screen alone cannot prove existing elements update.
3. Check representative buttons, inputs, selections, panels, status/validation/focus/disabled states in both modes. Review every introduced control's applicable visual tree for bypassed resources and stale references.
4. Check multiple supported window sizes and Windows scaling settings, longer text, different font rendering, and appearance switching at those sizes. Record clipping/overlap/scrolling/performance outcomes; do not invent supported sizes or measurements.
5. Audit XAML/C# for theme-owned literal colors/brushes/radii/typography/effects/dimensions, local Light/Dark values, copied global styles, and per-card theme branches. Confirm any data-specific/exceptional styling is narrow and documented.
6. Review the future-theme addition process against the actual implementation: complete variants can be registered without screen rewrites, shared-control replacement, or unrelated logic edits. No extra theme implementation is allowed to demonstrate this.
7. Confirm Phase 01 contains only Bento Light/Dark, non-visual engine, Bento-owned reusable styles and Theme Studio. Build success alone does not prove switching, layout or visual correctness. Report runtime checks as incomplete if Windows execution is unavailable.

Phase 00 checks must additionally confirm the exact eight-theme order, Bento as primary, Claymorphism second, Phase 01 restriction, dynamic-theme coverage, no contradictory active instructions, and no product implementation. Stop for explicit approval.

## Research-to-review loop and evidence

Execute the permanent loop in [AGENTS.md](../AGENTS.md): **Research → Design specification → Implementation → Build → Runtime inspection → Comparison → Correction → Regression verification → User review**. Record research URLs and actual patterns inspected/adapted to WPF; approve concrete Light/Dark design values before implementation. Compare runtime output to the specification, record discrepancies, fix shared resources/components, and rerun affected build/tests/runtime checks after corrections. Retain actual outcomes and unresolved limitations, not fabricated screenshots or blanket coverage claims. User review must precede any Claymorphism implementation.

Review placement as well as behavior: all theme definitions, services, validation, effects and reusable theme styles must be under Theme, in the shared or individual location specified by Project Rules. Studio must remain a consumer. Check file responsibilities before adding files, explain necessary abstractions/dependencies, and remove unused code/resources introduced by the task only. Phase 00 neither creates this planned directory tree nor completes the visual research/implementation loop.
